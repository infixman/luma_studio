# 課程商城開發總覽

這份文件記錄整個開發過程：做了什麼、審查發現什麼、修了什麼、以及**我自己下的判斷**。
持續更新，不另開新檔。

寫給之後要看的人，所以用白話。技術細節在各 phase 的 `spec.md` / `design.md` 裡。

---

## 一句話說這個專案在做什麼

原本的商城只能賣「有庫存、要寄送」的實體商品。現在要能賣線上課程，還要能賣
「課程 + 材料包」這種混合商品。

難點不是多加一個商品類型，而是**同一個購物車、結帳、訂單流程要同時處理**
「要寄的」和「要開通的」兩種東西。

---

## 核心設計：四層拆開

```
商品 Product      → 只管展示（名稱、圖片、上不上架）
方案 Offer        → 只管定價（顧客實際買的單位）
內容 Component    → 只管「這個方案付款後給什麼」
交付目標          → 課程 Course（開通觀看）或 庫存品 InventoryItem（出貨）
```

### 為什麼不用「商品類型」欄位

最直覺的做法是加一個欄位寫「這是實體 / 數位 / 混合」。**沒有這樣做**，因為那個欄位會漂移：

管理員今天把材料包從方案裡拿掉，如果忘了同步改欄位，系統就會以為還要出貨。
兩邊不一致的後果是「把數位商品寄出去」或「把實體商品搞丟」。

所以「要不要配送」「有沒有含課程」全部是**當下從內容清單推導出來的**，不存在資料庫裡，
前端也不准提交這些值（提交了直接回 400，不是忽略 —— 忽略會讓呼叫端以為被採納了）。

### 為什麼庫存要獨立出來

原本庫存數字掛在「方案」上。一個材料包同時被三個課程方案使用時，
數字放在其中一個方案上，對另外兩個就是錯的。

所以庫存搬到獨立的「庫存品」，三個方案共用同一批數量。

## 已經定案的商業規則（2026-07-30）

這八項原本是待決策，現在都定了。每一項都直接影響程式怎麼寫：

| 議題 | 決定 | 白話 |
|---|---|---|
| 退款後還能看嗎 | 自動收回 | 全額退款會停掉觀看權，但不刪觀看進度和訂單紀錄 |
| 混合商品何時開課 | 付款後立刻 | 不用等材料包寄到 |
| 觀看期限怎麼算 | **從第一次觀看起算** | 不是從購買日起算 |
| 課程能買幾份 | 一份 | 已經擁有的課程不能再買 |
| 免運門檻怎麼算 | 只算要寄的部分 | 買課程不會把訂單推過免運門檻 |
| 純課程訂單狀態 | 開通成功就完成 | 沒有出貨流程 |
| 課程封存後 | 已購買的人繼續看 | 封存只擋新的販售 |
| 能不能送課程 | 可以 | 但不會產生一筆零元訂單 |

**「從第一次觀看起算」是最影響實作的一項。**
付款時只記「幾天」，不算到期日；要等會員真的按下播放才開始倒數。
理由：不然還在等材料包寄到的會員，觀看期限就先被消耗掉了。

## 我自己下的判斷（你可以推翻）

這些不是文件裡寫死的，是我在實作時遇到選擇、自己決定的。列出來給你檢查。

### 1. 庫存品的編號沿用方案編號

搬移舊資料時，每個方案會生出一筆對應的「庫存品」。這筆庫存品的編號我直接沿用方案的編號。

- **好處**：搬移程式可以重複執行不出錯、不需要額外的對照表、日後查資料一眼看得出來源
- **代價**：兩張表裡有一樣的編號，看 log 時要多想一秒

你在 7/30 確認「維持」。

### 2. 草稿課程可以先加進方案，但方案不能上架

原本可以設計成「課程沒發布就不准加進方案」。**沒有這樣做**，因為那會強迫管理員
一定要先把課程做完才能建商品。

改成：加的時候放行，但方案要啟用時會擋下來，並明確說「課程 X 尚未發布」。

### 3. 商品編輯頁的庫存欄位，共用的庫存品不給改

商品編輯頁上那個「庫存」欄位，只有在該方案剛好對應唯一一個、且沒有被別人共用的
庫存品時才能改。

其他情況直接拒絕並說「請到庫存品管理調整」。因為共用的數量屬於所有使用它的方案，
從某個商品頁改掉會靜默影響其他商品。

### 4. `variant.stock` 這個舊欄位還留著，而且還在寫

理想上庫存只該有一個來源。但訂單的扣庫存要到 Phase 3 才搬完，現在拿掉舊欄位
會讓商城賣出不存在的庫存。

所以舊欄位降級成「鏡像」，只由**一個函式**寫入，Phase 7 清理時只要刪那一行。
已記錄在 Phase 2 的 task 文件裡，不是漏掉。

### 5. 前端測試環境選了 happy-dom，沒裝 testing-library

專案原本沒有能渲染畫面的測試。加了 `happy-dom`（一個 devDep），
用 Preact 自己的 render + 原生 DOM 查詢，沒有引入 testing-library。

理由：這個專案相依很精簡，能用內建的就不多加一層。

### 6. 舊購物車格式的相容期訂為「兩個前端版本 + 90 天」

購物車存在瀏覽器裡而且**沒有過期時間**，久沒回訪的顧客可能還存著幾個月前的舊格式。
縮短這個數字等於選擇讓那些人的購物車靜默清空。

### 7. 重複購買鎖放在 Phase 3 而不是 Phase 2

「不能重複購買已擁有的課程」需要一張鎖表。我把它放在 Phase 3（結帳併發保護），
不是 Phase 2（建表）。也可以主張跟其他新表一起建。

## 過程中找到的真實 bug

都是**先寫測試讓它失敗，再修**。這樣才知道測試真的抓得到。

| # | Bug | 影響 | 怎麼發現的 |
|---|---|---|---|
| 1 | `update_variant` 少傳一個參數 | 商品編輯頁儲存售價庫存**直接壞掉** | Phase 2 接線時發現 |
| 2 | 上架中卻沒有可販售方案的商品沒人管 | 顧客看得到、買不了 | 盤點 Phase 1 缺口時 |
| 3 | 庫存品搜尋有競態 | 打字快時會顯示錯誤的搜尋結果 | 審查指出 |
| 4 | 內容數量每按一鍵就存一次 | 打「12」會先送 1；清空欄位會送 NaN | 審查指出 |
| 5 | 警告訊息的 key 重複 | 三門未發布課程會產生重複 key | 審查指出 |
| 6 | **純文字單元跳過了權限檢查** | 沒買課程的人可以對它寫觀看進度，而且進度算在他宣稱的任何課程上 | 最終審查指出 |
| 7 | **後端做完了、前端沒接** ×4 | 見下方「四個斷點」——功能實際上跑不起來 | 完工後自我盤點 |

**第 1 個最值得說**：Phase 1 的工作清單把「更新單一商品時同步更新方案」打勾了，
但沒有測試涵蓋，所以這個一定會爆的錯放到現在才被發現。

**第 6 個是最危險的**：判斷「這個單元能不能播」時，我把「有沒有影片」的檢查
寫在「有沒有買」的**前面**。結果純文字單元對所有人都回答「沒有影片」——
包括沒買課程的人。而上層又把「沒有影片」當成無害（因為閱讀單元本來就該能標記完成），
於是就變成：沒買課程的人可以寫進度，而且課程 ID 是他自己送的。

檢查順序調換就修好了。教訓是**授權檢查要放在所有其他判斷之前**，
不然任何一個「無害的提前返回」都可能變成一個洞。

## 審查建議我沒有採納的

### 「`_component_view` 重複查詢，拿掉省一次」

拿掉會製造 bug。

`resolve_offer` 會**故意丟棄**「目標已封存」的內容 —— 購物車不能報價出貨不了的東西。
但編輯器正是拿來移除那個壞掉內容的畫面，它不能移除自己沒被顯示的東西。

已在程式碼註解寫清楚，免得下次有人又想「優化」掉。

### 「useEffect 缺少 cleanup」

Preact 不像 React 會對此發出警告，而且這些頁面只在掛載時載入一次。
真正會出問題的情境（較慢的舊請求蓋掉新結果）已經在第 3 項單獨修掉了。

## Phase 3：購物車、結帳、訂單、開通

已完成：
- 資料表（訂單交付快照、會員權限、權限來源、重複購買鎖）
- 權限授予與撤銷的邏輯（可重複執行，付款通知重送不會出問題）
- 購物車改走統一的展開邏輯，純課程不問配送
- 訂單建立改扣庫存品、寫交付快照
- 結帳 API 條件式欄位：**先算價，再決定要哪些欄位**。純課程不要配送方式、不要電話、不要地址；姓名還是要（收據和通知信要用）
- 付款後開通：`provision_paid_order`

- 訂單頁分開顯示「數位內容」和「待出貨內容」（顧客端與後台都做了）
- 純數位訂單不能被標記出貨（後端擋 + 後台不顯示按鈕）

- 重複購買鎖串接完成

待做：
- 退款撤銷的管理介面（Phase 7）

### 為什麼需要「重複購買鎖」

購物車會說「你已經擁有這門課」，但**購物車是一個畫面，不是保證**。
開兩個分頁、或在慢速網路下連點兩次，兩邊都會在訂單成立前通過那個檢查。

所以結帳時要先搶一把鎖（同一個會員 + 同一個方案只能有一把）。搶不到的那筆直接被擋下。

三個細節：

- **鎖在扣庫存之前搶**。要把人擋下來，就在還沒為他從架上拿走任何東西之前擋。
- **過期的鎖可以被接管**。有人結帳到一半跑掉，不能讓他從此再也買不了這門課。
- **付款後鎖不再過期**。已付款的鎖要留著，否則十五分鐘後同一個人又能再買一次。

### 訂單頁為什麼要分區

課程在付款當下就能看，材料包不能。混在同一張清單裡，整筆訂單看起來都還在路上，
已經拿到觀看權的會員會去找一個不存在的物流單號。

所以分成「數位內容 / 已開通」和「待出貨內容」兩區。純數位訂單連「收件資料」卡片都不顯示
—— 一整張空欄位看起來像資料遺失。

### 一個防呆的預設值選擇

後台的「標記已出貨」按鈕，在拿不到 `hasPhysical` 這個欄位時**仍然顯示**。

看起來不安全，但反過來想：這種情況只會發生在「後台比 API 新」的時候，
而部署順序是後端先上，所以那代表發生了回滾。這時候把按鈕藏起來，
真正有包裹要寄的訂單就出不了貨。顯示它最多換來一個伺服器本來就會回的錯誤。

已抽成 `shippableMoves` 並用測試把三種情況都釘住。

### 付款後開通的一個關鍵細節

`provision_paid_order` 的呼叫**故意放在「狀態真的改變了」的判斷之外**。

如果放在裡面：第一次付款通知進來，狀態改成已付款，但開通課程時失敗了。
第二次通知進來，發現訂單已經是已付款，於是跳過整段 —— 這個會員就永遠拿不到課程。

放在外面，每次通知都會嘗試補開通，已經開通過的會被 SQL 條件擋掉。

### 純數位訂單會自己完成

沒有包裹要寄，就沒有人會去把它從「已付款」推到「已完成」。所以開通全部成功後自動轉完成。

但**只有在全部成功之後**。開通失敗卻標成已完成，等於用一個綠勾把問題蓋住。

## Phase 4：影片上傳與轉檔

### 決策變更（2026-07-30）：不用 Cloudflare Container

原計畫是自建轉檔管線 —— 一個 TypeScript 媒體 Worker、Queue、跑 FFmpeg 的 Container。
你決定不承擔它的持續費用與運維面積。Cloudflare 平台上沒有便宜的替代品：Stream
按觀看分鐘計費，Worker 不能跑 FFmpeg。

所以轉檔跑在你的機器上。素材本來就在那裡，CPU 已經付過錢了。

| 原設計 | 定論 |
|---|---|
| Container 跑 FFmpeg | 桌面工具在你的機器上跑 |
| Queue 排程與重試 | 不需要；轉檔失敗就在本機重跑 |
| 瀏覽器 multipart 直傳 | 桌面工具向 Admin API 要 presigned URL 後直傳 |
| Media Control Worker（TypeScript） | 不需要；簽章在既有的 Admin Worker 裡 |

**中間我走錯一次，記在這裡。** 我先寫了 `scripts/transcode-course-video.ps1`
＋ rclone，並宣稱「不需要 SigV4 了」。那是把兩件事混在一起：轉檔跑在哪裡，
跟上傳從哪裡發起，是兩個獨立的決定，我擅自改了第二個。你要的是從介面挑一個檔案就
結束，不是背指令。所以上傳仍然是 presigned URL 直傳，SigV4 還是要做 ——
只是簽章在 Admin Worker 裡，不必為它多開一個 Worker（`hmac`／`hashlib` 在這個
runtime 可以用，播放 token 已經證明了）。

腳本留著只是為了對照，ingest 的正路是 `desktop/` 的 Electron 工具。

### 桌面工具的那條硬線

**R2 的金鑰不進工具。** 工具會裝在筆電上、安裝檔會放在網路上，任何寫進去的長效
金鑰等於公開的長效金鑰。工具拿到的是只能做影片操作的短效 token，每個 S3 動作都
向 Admin API 換一張限定 bucket、key、method、期限的 presigned URL。

最壞情況因此是「有人可以上傳影片」，而不是「有人可以改訂單」。

驗證身分用配對碼：後台顯示一組 TOTP 數字，工具送 email ＋ 數字換 token。
「能看到後台」就是「能授權一台機器」，桌面上不留任何能登入後台的東西。

ffmpeg 只從我們的 R2 鏡像抓，版本與 SHA256 釘死。你原本想先試官方連結省 R2 流量
—— R2 沒有 egress 費用，那是它跟 S3 最主要的差別，所以省不到；而「官方失敗就退回
鏡像」等於把最少被測到的那條路留到官方真的壞掉那天才第一次執行。一條路就好。
（FFmpeg 是 GPL，我們一託管就是散布，所以 LICENSE 與原始碼一起鏡像。這個義務跟
從哪裡下載無關。）

### 驗證變得更重要，不是更不重要

一支影片幾百個物件，**少傳一個是常態**。而少一個分段的影片會播到那一段才斷 ——
這是最糟的發現時機。

所以 `video.verify_encode` 會讀 master playlist、逐一確認每個被引用的物件真的存在，
**一次回報所有缺漏**（讓你補傳一次，而不是補傳六次）。

三個容易漏掉的檢查點：

- **init segment 藏在 `EXT-X-MAP` 標籤裡**，不在自己的一行。播放器有全部分段卻少了它，
  一段都解不出來 —— 很容易從檢查清單裡漏掉，而代價很高。
- **不是 playlist 的檔案回傳空清單**，而不是回傳它的每一行。呼叫端會把每一行當成路徑去抓。
- **`../` 直接拒絕。** playlist 是別人上傳的檔案，跟著它跳出自己的資料夾，
  等於讓一次上傳決定驗證器（以後還有閘道）去讀 bucket 裡的什麼。

### 保留下來的東西

資料表、物件路徑、狀態機、畫質階梯、播放閘道都照原設計實作，沒有改。
日後想自動化轉檔，這些都還在，只需要補上排程與執行環境。

註冊端點寫進 `ready` 是**唯一繞過狀態機的地方** —— 而且只在驗證通過之後。

### 原始檔留在 R2，這件事比看起來重要

你問過 source 桶能不能刪。空桶不收費，所以刪它省不到錢 —— 真正的問題是
「原始檔要不要有第二份，在筆電之外」。

答案是要，理由不是備份，是**階梯沒辦法從階梯重建**。加一階畫質、修一支轉壞的、
補回 R2 掉掉的物件，每一件都要回到原始檔。順帶也真的是備份：筆電和 Cloudflare
是兩個失效域 —— 但只在本機那份也留著的時候。

而原始檔在 R2 上，「重新轉檔」就從「找出當初那台筆電」變成「任何裝了工具的機器」。
這個功能幾乎不用改架構：版本化 key、`ready -> queued`、驗證後才切 active，
當初都已經在那裡了。只要補一個 presigned GET。

### 保存政策：不設 lifecycle rule

唯一的硬規則是「課程還在用的東西不刪」，而且是**不給刪除入口**，不是給個警告。
其餘原始檔可以刪，但要逐項確認，確認文字要寫出「刪了就不能再重新轉檔」。

刻意不設任何依時間刪除的規則。設了就等於讓重新轉檔對舊影片默默失效，而那要到
有人按下重新轉檔的那天才會發現。

真正該定期清的是孤兒 —— 上傳中斷留下的殘骸。工具只能新增不能刪除，所以這些只會
累積。**輸出桶的孤兒會比原始檔桶多得多**：一次中斷留下的是幾百個物件，不是一個。
這裡有一個很容易踩的坑：**正在上傳中的版本長得跟孤兒一模一樣**，因為它那一列還
沒寫進 D1。所以盤點要排除 `uploading` 的 asset，還要加一個年齡門檻。

### 容量不能靠列 bucket 算

後台要醒目顯示容量和每月費用（不然沒有人會想起該清東西）。但一支影片幾百個物件，
總覽頁每次開就列幾千個 key，慢又燒 Class B 操作。

`verify_encode` 為了驗證本來就會 HEAD 每一個物件 —— **那時候就拿得到大小**。
所以總量在註冊時記進 D1，總覽只讀 D1。需要真的列 bucket 的只有找孤兒，
那是一個有進度、可以隔很久跑一次的動作。

這也逼出一張本來沒有的表：`video_encode_versions`。版本原本是隱含的（只有
`active_encode_version` 一個數字），被取代的版本在 D1 裡沒有痕跡。要算容量、
要列出可以刪的舊版本、要判斷輸出桶的孤兒，都需要那些版本有名字。

費用的單價做成設定值而不是常數。R2 價目會變，而**一個過期的數字比沒有數字更糟，
因為它看起來像事實**。

### 還沒做

整個桌面工具，以及它需要的後端。分成八階，風險大的先做（S1 是 SigV4，錯了後面
全要改），S4 結束是第一個能用的版本，之後每一階都可以獨立延後。清單見
`plans/…phase4…/task.md`。

影片庫的畫面（列表與封存的 API 都完成了）。真實媒體檔的 fixture 測試
（直式、無音軌、可變幀率、損壞檔）需要實際檔案。

## Phase 5：課程編輯

不需要新資源，所以完整做了後端。

### 已完成

- 課程展示欄位（簡介、封面、講師、難度、語言、適合對象、學習成果…）
- 章節與單元
- 大綱驗證、發布檢查、公開資料形狀
- 管理 API：大綱讀寫、發布、封存

### 幾個刻意的決定

**單元不存影片長度。** 長度屬於影片本身，抄一份在這裡的話，影片一重新轉檔就錯了。

**大綱是整棵樹一起驗證、一起替換。** 替換等於先刪掉舊的，如果驗證到一半才發現某個單元
有問題，課程會少掉一半章節而且沒東西可以放回去。

**排序用「送過來的順序」，不用前端給的數字。** 前端會送重複的、跳號的、99 的，
它真正的意思是「這個順序」。

**發布檢查一次回報全部問題。** 每存一次只知道一個問題、修完才發現下一個，是很糟的下午。

**沒有影片的單元可以發布。** 純文字的閱讀單元是合理的。但「指定了影片、而影片還在轉檔」
會被擋下 —— 那等於賣一個轉圈圈的載入畫面。

**公開資料會列出每個單元的名稱，但只有試看單元附內容。** 知道課程教什麼正是商品頁的用途；
其餘是付費才有的。而且**沒有任何單元會帶影片的 ID** —— ID 是可以拿去找東西的，
播放權要靠 Phase 6 的閘道驗證，不能靠「知道名字」。

**`published_at` 只記第一次。** 編輯後重新發布不是一門新課程，覆蓋掉會失去「什麼時候真正上架」。

## Phase 6：會員觀看與播放授權

### 核心取捨：只在發播放權時查一次資料庫

一堂課會產生**幾百次**影片分段請求。如果每次都去查「這個人買了嗎」，
成本會高過它保護的東西。

所以改成：建立播放 session 時查一次，然後發一張**短效簽章 token**。
之後每個分段只驗簽章，不碰資料庫。

代價是「取消觀看權」不會立刻生效，要等目前這張 token 過期（十五分鐘內）。
這是刻意的取捨，不是疏漏。

### Token 的設計重點都是無聊的那些

- **寫明它開的是哪一支影片、哪一個轉檔版本** —— 一堂課的 token 不能打開整門課，
  舊版的 token 也不能碰新版
- **會過期**，而且「從未來簽發的」直接拒絕（時鐘誤差很小，來自未來的 token 不是誤差）
- **常數時間比對** —— 一個遇到第一個錯字元就停的比較，會告訴攻擊者他猜對了多少，
  一次一個請求
- **驗證時接受前一把金鑰，簽發只用現在這把** —— 換金鑰不能讓所有會員在課上到一半被登出
- **失敗一律回 None** —— 「過期」和「偽造」對正在試探的人來說是同一個答案，
  差別記在 log 裡

### 路徑用白名單，不用黑名單

只接受轉檔程式實際會產生的那幾種檔名。每一份「traversal 手法清單」都會漏掉一種，
而這些檔名完全可預測，沒有理由接受別的。

### 觀看期限在這裡才開始算

付款時只記「幾天」。真正開始倒數是在**第一次成功取得播放權**的時候，
用一個帶條件的 UPDATE（`first_viewed_at IS NULL`）保證只成功一次。

沒有這個條件的話，每按一次播放都會重設，三十天的課程就變成永久的了。

### 這不是 DRM

能看的人可以錄下他看到的東西。目標是「不能看的人看不到」，
以及「脫離情境被分享出去的網址會很快失效」。文件裡明白寫出來，不誇大。

## Phase 7：營運工具

### 對帳查詢：專門找「應該發生卻沒發生」的事

每一支查詢都對應一種會靜默發生的失敗：

| 找什麼 | 為什麼重要 |
|---|---|
| 已付款但課程沒開通 | 顧客**立刻就會感覺到**，而且他自己無能為力 |
| 逾期卻還佔著庫存 | 定時工作漏掉的那些（部署中斷、isolate 死掉） |
| 卡住的上傳或轉檔 | 中途放棄的那一次會讓那個版本一直鎖著，重試也進不來 |
| 所有來源都撤銷了、權限卻還在 | **有人在看一門已經退費的課**，正常流程永遠不會發現 |
| 孤兒的購買鎖 | 會員被告知「你已經擁有」一個他其實沒有的東西 |

**這些查詢只找，不修。** 修的工作交給本來就知道怎麼修的程式碼
（`provision_paid_order`、`release_stock`）。同一個修復寫兩遍，就會有兩種行為。

查詢範圍也刻意窄。一支會回傳全部東西的掃描，是沒有人敢按的掃描。

### 功能開關放在伺服器

前端可以用開關決定要不要畫按鈕，但**後端用它決定要不要允許**。
「把按鈕藏起來」從來沒有阻止過任何人直接呼叫底下那支 API，而那支 API 才是收錢的。

兩個細節：

- **沒設定就是關閉**。沒有被告知要賣課程的部署，不該因為少一個變數就開始賣。
- **只有 `"1"` 算開啟**。也接受 "true" 的話會變成兩種拼法、然後三種，
  最後有一種在關鍵時刻默默失效。

### 退款：部分退款一定要指名

全額退款會撤銷這張訂單給出的所有課程。部分退款**必須明確指出撤銷哪幾筆** ——
從退款金額反推「他該失去哪一門課」是在猜，而被猜的東西是某個人的觀看權。

送了空清單的部分退款直接拒絕，不是默默什麼都不做。

## 課程編輯器

之前只能看不能改，所以**實際上沒辦法建立一門課**。現在可以了。

### 大綱編輯

章節與單元都能新增、移除、上下移動。影片從已完成轉檔的清單裡選，也可以不選（純文字單元）。

三個實作上的決定：

**整棵樹一起送。** 伺服器是整組替換的，所以編輯器持有一份草稿、由頁面一次存。
每一列各自存的話，任何一次失敗都會留下改一半的大綱 —— 半門課比沒存還糟。

**每次變動都重新編號。** `position` 是伺服器排序的依據，只調整陣列順序而不重新編號，
存下去會是作者原本的順序。

**只列出轉檔完成的影片。** 指向還在轉檔的影片無法發布，在這裡提供它只會在稍後產生一個錯誤。

**移除章節會說「裡面的 N 個單元會一起移除」。** 這件事不明顯，而且無法還原。

### 長文欄位

「你將學會 / 適合對象 / 課程介紹 / 先備知識 / 需要準備的工具 / 講師介紹」六個欄位
用既有的 rich text editor。順序照著「一個正在決定要不要買的人」閱讀的順序排。

HTML 一律在後端清理。有一個測試特別驗證**六個欄位都經過同一道門** ——
漏掉其中一個正是不會被發現的那種失誤。

### 未儲存警告

離開時會確認。因為未存的不只是一個欄位，是整份大綱。

### 一個測試上的教訓

我原本寫「檢查回傳的 HTML 沒有 script」，但假資料庫回傳的是原始 fixture 不是寫入值，
所以那個測試**通過但什麼都沒驗到**。改成直接測「路由組出來的東西」而不是「讀回來的東西」。

這是這個專案裡第三個假通過的測試了。共同點都是：斷言的對象不是實際發生變化的地方。

## 給之後的人：幾個容易誤解的地方

1. **「方案」和「規格」是同一件事的兩個名字**。程式裡舊的叫 `variant`，新的叫 `offer`，值是一樣的。
2. **觀看期限不是從購買算**。文案一律寫「觀看後 N 天」，不要寫成「購買後 N 天」，那是不同的商品。
3. **一個會員一門課只有一筆權限，但可以有多個「來源」**。買兩次同一門課 = 一筆權限 + 兩個來源。退掉其中一次只會撤掉那個來源，權限還在。這是退款不會誤傷的關鍵。
4. **`expires_at` 是 NULL 有兩種意思**：永久，或是有期限但還沒開始看。兩種都算有效。

## 四個斷點：後端做完了、前端沒接

這是最值得記下來的一類問題：每一項的伺服器端都寫好也測過了，但**從瀏覽器碰不到**。
測試全綠，功能不能用。

### 1. 結帳頁還在要求電話與地址

後端已經改成「純課程不要求配送方式、電話、地址」，前端沒跟上。
買課程的顧客會停在一張問他「要寄到哪裡」的表單前，而且送出鍵在選了配送方式之前是停用的
—— 純數位購物車永遠不會被提供配送方式，所以那個鍵永遠按不下去。

現在請求只帶這筆訂單真正有的欄位。

### 2. 播放器只有 Safari 能用

`<video src="....m3u8">` 在 Safari 可以播，Chrome 和 Firefox 不行 ——
而且失敗的方式是「永遠不出現畫面」，看起來像影片壞掉而不是缺少解碼器。

改用 hls.js，而且是**按需載入**不打包進商城：大部分造訪是在購物不是在看課。

### 3. 學習頁完全沒有存進度

後端有 API，前端沒呼叫。所以「繼續上課」永遠回到第一課，完成數字永遠是 0。

寫入節流到 20 秒 —— `timeupdate` 一秒觸發好幾次，而這是只會被讀一次的資訊。
但**大幅往前拉會立刻寫入**：他已經移動了，等 20 秒的話關掉分頁就丟了。
失敗刻意吞掉：掉一次進度是倒退 20 秒，在正在播放的影片上蓋一個錯誤橫幅是失去這堂課。

### 4. 商品頁完全沒有課程資訊

公開 API 也沒回。顧客在商品頁看不到大綱、講師、時數。

課程會**跨方案去重** —— 「線上版」和「課程＋材料包」通常給同一門課，
列兩次會讀成兩門不同的課。每個單元都列出名稱（知道教什麼正是這一頁的用途），
只有試看單元附內容。純實體商品完全不查這些。

### 教訓

「後端測試全綠」和「使用者能用」是兩件事。每一個階段結束時應該問的是
**「現在有人能從瀏覽器走完這件事嗎」**，而不是「測試過了嗎」。

# 桌面上傳工具的實作紀錄

分成八階，每一階再切成「跑起來不會壞」的最小步驟。每個步驟開發完先做三次審查
（一致性、對抗性、重構），修完才 commit。

## S1.1：SigV4 簽章

`backend/src/shared/sigv4.py`。整條路的地基 —— 桌面工具能對 R2 做的每一件事，
都是這裡簽出來的，所以它先做。

### 用 botocore 當 oracle

簽章只有兩種結果：**跟 AWS 規範一個 byte 不差，或者 R2 回一個什麼都沒說的 403。**
自己寫的簽章「差一點對」的時候，錯誤訊息不會告訴你是十幾條 canonical 規則裡的哪一條。

所以測試不是驗「程式做了程式做的事」，而是驗**同一份輸入，botocore 簽出來一樣**。
botocore 在開發環境有，這比背一串 hex 常數可靠得多 —— 它是 test-only，
`src/` 底下不准 import（Workers runtime 裡沒有它）。

參數化五種真實的 key（master、segment、poster、source、init）加 GET/HEAD/PUT，
全部對上。

### 一個以為是 bug 的分歧

我加了一個含空白和 `+` 的 key 做編碼測試，簽章對不上。查下去發現不是我的錯：
**botocore 對 S3 完全按傳進去的 URL 路徑簽，不重新編碼**（因為 S3 的 key 是字面值）。
我傳它未編碼的路徑，它就簽了那個原始空白；我這邊簽的是 `%20`。

傳它已編碼的路徑，兩邊一致。所以我的編碼符合 AWS 的 canonical URI 規則，是測試
自己拿蘋果比橘子。這件事寫進那個測試的 docstring 了，不然下一個人會讀成
「我們跟 botocore 不一樣」。

### 對抗性審查找到四個

1. **bucket 沒驗形狀。** `_encode` 不編碼 `.`，所以 bucket 若是 `..` 就在簽好的
   路徑裡造出一個穿越。bucket 來自設定不是請求，但這個模組就是安全邊界，
   一行檢查換掉「要推理每一個未來的呼叫者」。
2. **endpoint 若含路徑**（`https://host/path`），host header 會被簽成 `host/path`，
   R2 讀成完全不同的主機 —— 錯得很安靜，而且只會表現為 403。
3. **query 我先排序再編碼。** 這五個固定名稱編碼後不變，所以今天沒差；但 AWS 的
   規則是排**編碼後**的值，日後加一個帶特殊字元的參數就會排到不同位置，
   而失敗長相仍然是一個空的 403。改成先編碼再排。
4. canonical path 算了兩次。抽出來算一次。

### 刻意不做的

- **沒有 presigned DELETE。** `METHODS` 只有 GET／HEAD／PUT。刪除是後台的工作，
  引用檢查在那裡。不是靠呼叫端自律，是簽不出來。
- **沒有 prefix 級的簽章。** 一張 URL 一個物件。
- `now` 當參數傳入，不讀時鐘 —— 跟 `playback.issue` 同一個理由：結果是參數的函數。

### 一個確認過的假設

`urllib.parse.quote` 在 Workers runtime 能用 —— 不是猜的，`domain/bio_link.py`
已經在生產環境用它。這是這個階段唯一的 runtime 依賴。

## S1.2：什麼 key 簽得出來

`video.signable_key`。簽章能簽任何 key，所以「只能簽這個 asset、這個版本、
這一個物件」是另一件事，而它比簽章本身更接近真正的邊界。

### 重構審查先擋下一份重複

寫之前先找「這個清單是不是已經存在」—— 存在。`playback.OBJECT_PATTERNS` 就是
「encoder 會產生哪些物件名」的清單，phase 6 為了播放閘道寫的。

如果我在 `video.py` 再寫一份給簽章用，**兩份清單的失效方向是相反的**：簽章決定
什麼能寫，閘道決定什麼能讀。哪天兩份走針，就會出現「上傳驗證通過、但會員播不了」
的資產。所以清單搬到 `video.py`（物件名是 encode 的屬性，不是開它的 token 的屬性），
`playback` 不再有自己那份，閘道改叫 `video.allowed_object`。

搬的時候順手修掉一個潛在 bug：舊的 patterns 把 `1080p|720p|480p` 寫死在正規表示式
裡，跟 `RENDITIONS` 各自一份。**加一階畫質只會改到其中一份**，結果就是簽得出來、
播不出來。現在 patterns 從 `RENDITIONS` 內插，並且有一個測試逐一走過 `RENDITION_NAMES`
確認每一階都能過，把耦合釘住。

### 一個 prefix 有五份

`videos/{id}/{v}/` 這個字串在程式裡有五份：三個 key builder、`verify_encode`，
還有播放閘道。

第五份最值得看：閘道是用**請求路徑帶進來的 asset_id** 手拼的，沒過
`ASSET_ID_PATTERN`。目前不能利用 —— R2 的 key 是字面字串，不會解析 `..`，
而且 token 也簽不出 `..` 的 asset —— 但那是靠**兩個巧合**成立的，不是靠檢查。

抽出 `encode_prefix()` 之後，asset id 與版本在一個地方驗證，五份變一份。

### 對抗性審查：測試自己沒被測到

`TestMediaCaching` 的 class docstring 寫著「授權在查快取之前」，這是 phase 6
最重要的順序之一 —— 快取鍵刻意不帶身分（所以可以共用），也因此一次未授權的命中
就會把一堂課開給所有人。

但那個 class 底下三個測試，**一個都沒有驗那個順序**。只驗了 `CACHEABLE_SUFFIXES`
的內容和 `is_cacheable()`。一句沒有測試撐著的話，而我剛好在動那個函式裡的順序。

補了兩個測試：沒有 token 的請求不能碰快取也不能碰 R2（用會記錄的假 bucket 和
被攔下來的 `_cached`），以及讀到的 key 就是 key helper 產生的那一個。

然後**用突變驗這兩個測試是真的**：把快取查詢搬到 token 檢查之前，測試掛掉。
這個專案我已經寫過三個假通過的測試，共同點都是「斷言的地方不是變化發生的地方」，
所以現在新測試一律突變一次再算完成。

### 刻意的選擇

- **`signable_key` 失敗時丟例外，不回 `False`。** 忘記檢查布林值的呼叫端會把
  拿到的東西直接簽出去，而這裡沒有安全的預設值。
- **`kind` 沒有預設。** `source` 與 `output` 決定的是哪個桶；日後多一個桶要來這裡
  明確加上，不會靜靜落到某一邊。
- 拒絕裡最重要的兩條：**別的 asset 的 prefix**（一次上傳寫進別人的影片），
  以及**同一個 asset 的別的版本**（宣稱要上傳新 encode，實際寫進會員正在看的那版）。

## S1.3：`POST /api/video-assets`

一列還沒有任何 bytes 的 asset。它得先存在，因為每一張 presigned URL 都綁定
一個 asset 和一個版本 —— 沒有 asset 就沒有東西可以綁。

起始狀態 `uploading`，而且只有 import 端點能把它推到 `ready`。

### 一個定義了但沒人用的開關

`VIDEO_UPLOAD_ENABLED` 在 `flags.py` 裡躺著，**沒有任何一行程式在檢查它**。
文件寫它要管 presign、上傳與註冊。

所以這一步順手把它接上：新的建立路由，以及既有的 import 路由。這會改變 import
的行為（沒設變數就 403），所以同時在 `wrangler.admin.toml` 補上 `= "1"` —— 部署後
行為不變，但現在有一個不需要重新部署就能關掉的開關。

它預設是「開」而不是「關」，理由跟課程結帳那個開關不同：這是後台能力，不是在賣的東西。
開關存在是為了出事時能立刻關掉。

### 對抗性審查：又一個「斷言在錯的地方」

三個測試我第一版是這樣寫的：

```python
assert response.json()["asset"]["status"] == "uploading"
```

**這什麼都沒驗。** 路由建立完會把 asset 讀回來，而假資料庫會用測試自己宣告的那一列
回答那個讀取 —— 所以我斷言的是 fixture，不是 insert。

改成從 `database.writes` 找出那一筆 `INSERT INTO video_assets`，驗語句裡有
`'uploading'`、驗寫進去的 id 過得了 `ASSET_ID_PATTERN`（因為那個 id 之後要進 object key，
產生一個 key builder 不接受的 id 會在第一次 presign 才炸）、驗 source key 是從 id 推的
而不是從檔名。

這是這個專案第四次同一個錯。共同點永遠是**斷言的地方不是變化發生的地方**。

### 重構審查抓到兩處重複

**上限有兩份。** `part_size_for` 裡有一次「不能超過 20 GiB」的檢查，新的建立路由
也需要同一個檢查。抽成 `validate_byte_size`，`part_size_for` 改成呼叫它。
兩份上限最後一定會不一致，而不一致的表現方式是「上傳開始了但傳不完」。

**同三個測量欄位有兩種處理方式。** import 路由本來是這樣寫的：

```python
duration_seconds=duration if isinstance(duration, int) else None,
```

也就是**壞值靜靜變成 None**。這跟這個檔案開頭自己寫的原則相反 ——「忽略它等於讓
client 以為被遵守了」。而且 `isinstance(True, int)` 是 `True`，所以送
`width: true` 會存成寬度 1。

抽成 `_measurements(body)`，兩條路徑共用，壞值一律 400。這是行為改變，補了測試。

## S1.4：發上傳 URL

`domain/video_storage.py` + `POST /api/video-assets/{id}/upload-urls`。
S1 的最後一步，也是這個階段真正的邊界 —— 工具沒有 R2 金鑰，所以它寫進 bucket 的
每一個 byte 都是這裡准的。

### 三個拒絕，順序不能換

1. **asset 必須還在 `uploading`。** 一支 `ready` 的影片，它的物件就是會員正在看的
   東西；發一張寫入 URL 給它，等於讓一次落後的重試蓋掉一個上線中的 encode。
2. **每個 key 都要屬於這個 asset 和這個版本。** 由 `video.signable_key` 回答，
   所以這裡不解析 key。
3. **一批不能太大。** 一個請求不可以變成幾千張有效憑證，因為 presigned URL 是
   bearer token，發出去就收不回來。上限 100，工具分批要。

### 整批驗，不是逐個發

一開始我寫成「能簽的簽、不能簽的跳過」。**那是錯的**：工具會以為它拿到了它問的
每一個檔案的 URL，然後在一次長上傳的最後才發現少了幾個 —— 最貴的時機。
一個 key 不合格，整批 400。有測試釘住。

### 沒設定的時候不要假裝簽好了

`NotConfigured` 是自己的例外型別，不是 `ValueError`，因為它不是呼叫端的錯，
不能用 400 回答。更重要的是：**發一張沒有簽章但長得像簽好的 URL**，會一路跑到 R2
才失敗，而那時候的 log 什麼都不會說。所以缺 endpoint 或缺金鑰一律 503。

三個設定各缺一個都有測試。

### bucket 名稱要寫兩次

R2 binding 給的是「一個可以讀寫的物件」，**不給 bucket 叫什麼名字**，而 presigned
URL 的路徑裡需要名字。所以 `wrangler.admin.toml` 裡 bucket 名稱出現兩次
（binding 一次、vars 一次），這是故意的，加了註解說明。

`R2_S3_ENDPOINT` 留空，因為我不知道帳號 id。留空的行為是 503，不是簽出一張壞的 URL。

### 驗「這是 PUT」要重新簽一次

method 是簽章的一部分，不會出現在 URL 的可讀欄位裡。所以測試的做法是：拿回應裡的
`X-Amz-Date` 和 `X-Amz-Expires`，用同樣的參數重簽一次 PUT 和一次 GET，
斷言 signature 等於 PUT 的、不等於 GET 的。

這件事值得測，因為 presigned GET 是「下載原始檔」的能力，屬於 S8 的重新轉檔，
不該從上傳路由漏出來。

### 重構審查：這次我決定不抽

flag 的檢查現在有三份（建立、import、presign），每份兩行。抽成一個
「回傳 response 或 None」的 guard 是可行的，但這個 codebase 沒有這種模式，
為了三份兩行的東西發明一個新模式更糟。而且哪些路由被閘門管著，明寫在路由裡比
藏在 helper 裡清楚。

真正會痛的重複是「必須互相同意的邏輯」，這個不是 —— 它是一次 flag 讀取。
到 S5 加了原始檔 multipart（四個子動作）再回來看。

### 已知的、刻意留著的

- **版本號從請求來。** 沒有 per-version 的表可以查（那是 S5 的
  `video_encode_versions`），所以 `encodeVersion` 是請求帶的，只做範圍檢查（1–999）。
  安全性由「key 一定要在那個版本的 prefix 底下」撐著，所以最壞情況是呼叫者在
  自己 asset 的一個沒人用的角落寫東西。
- **還沒有 rate limit。** 目前呼叫者是完整的管理員 session，`MAX_URLS` 限制了單次
  但沒限制頻率。跟 token 兌換的限流一起做（S2）。

### S1 完成

程式部分做完了。剩下的是你的動作：建 R2 的 S3 API token、把
`R2_S3_ENDPOINT` 的帳號 id 填上。填之前 presign 一律 503 —— 不會有「看起來成功
但其實壞掉」的中間狀態。

## S2.1：配對碼

`shared/totp.py`。

### 這個東西不是第二道密碼

伺服器**同時負責顯示和驗證**這組數字，所以它沒有帶來任何秘密性。它帶來的是
**一個不需要儲存狀態的時間界限**：一組碼在它那個時窗有效，過了就沒有。

這讓「看得到後台」和「能授權一台機器」變成同一件權限。不需要發什麼、追蹤什麼、
清理什麼。真正的秘密是 seed，它不離開伺服器。

### 用 SHA-1 不是因為偷懶

RFC 6238 標準組合：SHA-1、6 位數、30 秒、base32 seed。**今天沒有任何東西需要這個
標準性** —— 碼是從後台頁面讀的。但它免費，而且保留了一個選項：日後如果懶得開後台，
可以把 seed 丟進一般的驗證器 App，直接就能用。

測試同時對 RFC 6238 Appendix B 的公布數值和 pyotp 驗，兩邊都過。pyotp 是
test-only oracle，跟 botocore 一樣不准出現在 `src/`。

### 對抗性審查抓到一個 500

`verify` 我原本寫成「長度是 6 且 `isdigit()`」。

`"１２３４５６".isdigit()` 是 **True**（全形數字），而 `hmac.compare_digest` 對
非 ASCII 字串**會丟 TypeError 而不是回 False**。所以六個全形數字不是「配對碼錯誤」，
是一個 500。

加了 `isascii()`，補了全形與阿拉伯-印度數字的測試。這種東西不會有人手動試出來，
只會在某天的錯誤率報表上出現。

### 刻意不對稱

只接受**現在**和**前一個**時窗，不接受下一個。時鐘偏移理論上是雙向的，但管理員讀的
是同一個時鐘產生的碼 —— 往前開一格只是把猜測範圍多放大一半，換不到任何東西。

同樣刻意的：`code_at` 遇到壞 seed 會丟例外，`verify` 一律回 False。前者是給已登入的
管理員看的，壞 seed 是真的故障，該講出來；後者是給陌生人的，不能讓他分辨
「沒有 seed」和「碼錯了」。

### 重構審查

- **拿掉 `struct`。** `counter.to_bytes(8, "big")` 和 `int.from_bytes` 一樣清楚，
  而且少一個 runtime 依賴要擔心。
- `secure_bytes` 的 import 從函式裡搬到模組頂層，跟 `video.py` 一致。原本寫在函式裡
  沒有理由，只是我沒想清楚。

「用過即失效」不在這一層 —— 那需要記下用過什麼，是 S2.3 換 token 那一步的事。

## S2.2：配對碼頁面的後端

`domain/desktop_auth.py` + `GET /api/desktop/pairing-code`。

### 我先發現規格寫錯了

我在 spec 裡寫「seed 只以雜湊或加密形式保存」。**那是錯的** —— TOTP 的驗證方式是
重算一次那組數字，所以它需要 seed 原文，雜湊過就驗不了。

但這個錯誤逼出一個更好的答案：**根本不要存 seed。**

`seed = HMAC(DESKTOP_PAIRING_SECRET, "purpose:email")`

導出比儲存原文好，而且是每個面向都好：沒有表、沒有遷移、沒有「只顯示一次然後
希望對方記下來」的流程、D1 被 dump 也不含任何 seed。每個管理員的 seed 仍然不同，
因為 email 是導出的一部分。撤銷變成「換一個值」而不是「跑一次遷移」。

導出字串裡有一個 `PURPOSE` 常數做用途隔離。日後如果有第二個功能從同一個 secret
導東西，沒有隔離的話其中一個可以算出另一個的。

### email 要正規化

登入時會把 email 轉小寫再存。如果驗證時不轉，同一個人會有兩組 seed，
而症狀是**「正確的碼永遠對不上」** —— 這種東西很難從症狀回推原因。

### 撤銷有兩層

換 secret 一次撤銷所有配對。把某個 email 移出管理員允許清單，他就配對不了 ——
允許清單在 `verify_pairing` 裡檢查，不只在登入時。第二層很重要，因為換 secret 是
全體性的，而踢掉一個人不該影響其他人。

## S2.3：換 token 與 scope

### 先做一次純重構

token 的簽發驗證要出現第二份了。而**兩份會不一致的正好是最容易寫錯的部分**：
固定時間比較、無 padding 的 base64、拒絕未來簽發的 token、輪替時接受舊 secret。
在一份裡修好的 bug，在另一份裡會留著。

抽成 `shared/signed_token.py`，playback 改成呼叫它。prefix 當參數而不是常數 ——
兩個功能用不同 secret 本來就讀不了對方的 token，但不同 prefix 讓「種類不對」
在任何比較之前就被拒絕，而且改一邊的格式不會動到另一邊。

**playback 的 wire format 一個 byte 都沒變**，這是刻意的：會員現在手上就握著這些
字串，payload 一變就是所有正在上課的人被 403 到下次重新載入。做法是重構前後各簽
一次同樣的 token 然後比字串，確認一致，再把那個字串當 golden value 釘進測試 ——
共用實作本身就是「日後改那邊會靜靜改到這邊」的風險來源，所以那個釘子是必要的。

### 六位數字撐不住，所以另外三件事撐

配對碼是十的六次方。這個端點又是**不需要 session 就能打的**，所以撐住它的不是
碼本身難猜：

1. **一組碼只能用一次。** 它的時窗是 30 秒而且顯示在螢幕上，沒有這條的話，
   看一眼那個頁面等於拿到半分鐘內可重複使用的憑證。
2. **舊時窗不能在新時窗用過之後回頭用。** 接受前一個時窗是為了時鐘偏移，
   不是為了往回走。
3. **錯誤次數會累積並鎖定帳號。** 鎖定期間連正確的碼也擋 —— 鎖的是帳號，不是那次猜測。

### rate_limit 不能做第 3 件事

專案裡有 `shared/rate_limit.py`，但它**逐 IP、而且 binding 不存在時放行**
（模組開頭就寫明「一個能把網站弄掛的限流器比它防的濫用更糟」）。

那個取捨對公開頁面是對的，對六位數字是錯的：換 IP 就繞過，binding 掉了就完全不設限。
所以配對的次數上限在 D1、逐 email、失敗時關閉。這是同一個機制在不同場景要不同答案
的例子，不是誰寫錯了。

### FakeDatabase 評估不了 WHERE

單次使用的實作是條件 upsert：`ON CONFLICT(email) DO UPDATE ... WHERE used_counter
IS NULL OR used_counter < ?`。

假資料庫不會執行 WHERE，所以那道競態防護**在原有的測試裡完全沒有被驗到**。
補在真 SQLite 的測試檔裡（那個檔案本來就是為這種事存在的）。

而且測試不能自己抄一份 SQL —— 抄了之後改生產程式，測試還會過。所以 SQL 抽成
`CONSUME_SQL` 常數，測試 import 它。拔掉 WHERE 驗證過：兩個測試會掛。

### scope：允許清單，不是黑名單

`scope_allows(scope, method, path)` 只放行三條路由：建 asset、要 upload URL、註冊。
**不包含** `GET /api/video-assets`（列表是用來看別人上傳了什麼，工具知道自己剛建的
那一個）和 `archive`（刪除與封存屬於後台，引用檢查在那裡）。

method 也是比對的一部分，因為 `/api/video-assets` 的 GET 和 POST 是同一個路徑
不同意思。

驗證方式：把 `admin_main` 裡那道 403 拿掉，跑測試。**沒有它的時候 `/api/orders`、
`/api/customers`、`/api/dashboard`、`/api/session` 全都回 200 並且吐出資料。**
（我第一次讀輸出時以為只有四條掛，那是 `tail -4` 把前面截掉了 —— 八條都掛。）

### 一個答案回答所有失敗

「不是管理員」、「碼錯了」、「碼用過了」、「帳號鎖定中」都回同一個 401 和同一句話。
告訴對方「帳號已鎖定」就是告訴他猜到哪裡了。差別留在 log。

## S3.1：Electron 骨架

`desktop/`。一個視窗、一個版本號，其他什麼都沒有。

單獨切一步的理由：**Electron 最先壞掉的不是功能。** 是 preload 找不到、橋接沒出現、
打包後的畫面載不進來 —— 這三件事都表現為「一個空白視窗」，什麼訊息都沒有。
在半成品上傳器底下找這些，比現在找貴得多。

而且其中兩件真的是壞的：

### 一、top-level `await` 會 deadlock

Electron 的 `ready` 事件在入口模組**還在評估的時候**就該發生。所以
`await app.whenReady()` 寫在頂層等於：promise 要等評估結束才 resolve，
評估要等 promise resolve 才結束。

它不報錯，它就是掛著。而且我第一次除錯**一行輸出都沒有** —— 因為 buffer 跟著
被殺掉的進程一起死了。改成寫檔案才看到。

### 二、sandbox 的 preload 不能是 ESM

`package.json` 有 `type: module`，所以 electron-vite 產出 `.mjs`，而 Electron
拒絕載入一個 ESM 的 sandboxed preload —— `window.desktop` 是 undefined，
console 一片乾淨。

改成把 preload 建成 CJS，而不是關掉 sandbox。為了一個語法偏好放棄 sandbox 不划算。

### `npm run smoke`

抓到第二件的就是它：用真的 main bundle 跑 Electron、等視窗、**從頁面裡呼叫橋接**。
它是 `npm run build` 的一部分，因為「編譯過了」和「跑得起來」是兩件事，
而當時只有一件是真的。

## S3.2：配對畫面

### 一個我自己造的坑

後台把驗證碼顯示成 `418 302`（六位數字連在一起很難從螢幕上讀）。所以使用者會照著
打、照著貼。而伺服器只收六位數字。

**不清空格就會拒絕後台剛剛顯示的那組碼**，然後怪使用者。`normaliseCode` 把空格、
連字號、點、底線、還有某些客戶端會貼出來的不換行空格全部清掉。

### token 不進 renderer

所有需要 token 的請求都在 main process 發。renderer 問的是結果
（「用這組碼配對」、「現在有 session 嗎」），拿回來的是**關於** session 的事實，
不是 session 本身。`SessionStatus` 裡沒有 token。

理由跟整個 scope 設計一致：renderer 裡的 token 是任何一次腳本注入就能拿到的 token，
而「弄丟工具不等於弄丟商城」是這條線的全部意義。

### 沒有加密就不存

token 走 `safeStorage`（Windows 上是綁使用者帳號的 DPAPI）。
**作業系統不提供加密的機器上，什麼都不存。** Linux 沒有 keyring 就是這種情況，
而替代方案是「在最沒有保護能力的機器上把憑證明文寫進硬碟」。

代價是每次啟動要重新配對，而畫面會說明這件事，不會讓人自己發現配對留不住。

### 只有 localhost 可以不走 https

一個設定值錯了不是設定錯誤，是**憑證被交出去** —— 配對碼和之後每一個請求的 token
都在裡面。所以非 https 一律拒絕，只有 localhost 例外（它不離開這台機器）。

測試裡有一條 `http://localhost.evil.example`：只用字串包含判斷會放行它。

### 送出前先檢查形狀

六位數字後面有次數鎖定，所以送一個工具自己看得出來是錯的碼，等於白花一次額度。
一個「因為太熱心而把管理員鎖在門外」的工具比一個會說「這只有五位數」的工具糟。

失敗之後**清掉驗證碼欄位** —— 它反正已經失效了，留在框裡只會引誘人再按一次。

### 又是測試的問題

五個測試一開始全掛，看起來像 submit handler 沒跑。診斷之後發現 handler 有跑 ——
是**我在填欄位和送出之間沒有讓 Preact flush**。狀態更新是批次的，所以送出時
state 還是空的。

猜了兩次（改用 `requestSubmit`、改事件型別）都沒中，第三次才直接印出來看。
教訓跟後端那次一樣：**猜兩次的成本已經超過直接觀察。**

## S3.3：上傳一個已轉好的資料夾

輸入是 PowerShell 腳本的輸出目錄。這就是那支腳本還留在 repo 裡的理由：
**會出錯的是整合**（配對、簽章、重試、Content-Type、續傳、註冊），
而拿一份已知正確的輸出來試，比在當天寫的轉檔器底下找便宜得多。

### 三個順序決定，都不是為了好看

- **`master.m3u8` 最後傳。** 註冊會先讀它，所以中斷的上傳被拒絕時是「缺 master」
  一句話，而不是「缺三百個分段」—— 同一個事實，講得有用和沒用的差別。
- **每個物件設正確的 Content-Type。** playlist 以 octet-stream 送出，
  沒有播放器讀得懂，而 R2 會保留 PUT 當下說的那個值，所以只有這一次機會。
- **驗證是獨立顯示的階段**，不併進上傳。它是決定影片能不能播的那一步；
  「上傳完成」和「影片能播」是兩個不同的宣稱。

### 對抗性審查找到兩個真的錯

**一批的 100 張 URL 是一起簽的，只活 15 分鐘。** 一百個 1080p 分段在家用上傳頻寬下
可能超過那個時間，之後每個 PUT 都 403，整批在快傳完的時候死掉。現在過期的 URL 會
重換一次再試；換過還 403 才是真的拒絕。

**續傳的 ledger 用資料夾路徑當 key。** 同一個資料夾重新轉檔會產生一樣的相對路徑，
所以舊 ledger 會讓它接續到舊的 asset、跳過已經變更的檔案 —— **不會報錯，影片就是舊的那支。**
現在 key 裡加了檔案數和總容量。

### 兩個測試問題，跟前面同一個形狀

Preact 用「element 上有沒有 `ondrop` 這個屬性」來決定註冊 `'drop'` 還是 `'Drop'`，
而 happy-dom 沒有定義它 —— 所以 `onDrop` 註冊了一個永遠不會被觸發的監聽器，
**只在測試裡**。改成明確 `addEventListener`，把事件名寫出來而不是依賴那個判斷。

另一個：effect 是非同步的，所以 mount 和 drop 在同一個 tick 裡，
drop 到的是一個還沒有監聽器的元素。

## S3.4：打一次包，然後問它看得到什麼

打包後的 app 跟 `electron-vite dev` 是不同的程式：檔案在 asar 裡、
`import.meta.dirname` 解析到別的地方、`app.getPath('userData')` 才終於是它在別人機器上
的意思。之後每個功能都建立在這些路徑上（ffmpeg 放哪、ledger 放哪、token 放哪），
所以現在證實它們只要一次丟掉的打包，省下的是在轉檔器底下除錯。

`--self-check` 把它看得到的東西寫進自己的 userData 然後結束。這也是「它開不起來」
的答案：叫對方用這個旗標跑一次，把檔案傳來。

它證實了前一個 commit 只能主張的事：**打包後 `app.getVersion()` 回 `0.1.0`**
而不是 Electron 的版本，而 preload 和 renderer 都在 `app.asar` 裡解析正確。

## S4：本機轉檔

### 一個我做不完的部分，先說

設計是「ffmpeg 只從我們的 R2 鏡像抓，版本與 SHA256 釘死」。**那個鏡像還不存在。**

所以 `src/shared/ffmpegRelease.ts` 裡的 `PINNED` 是空的，而且**空的雜湊值一律當成
「尚未設定」，不會當成「跳過檢查」**。這是這個檔案唯一可能默默變成裝飾的方式，
所以有測試釘住：空字串、格式不對、大寫、63 位、65 位全部拒絕。

要填它需要你：挑一個 build、上傳到 R2、把版本／檔名／大小／雜湊寫進那個檔案。
在那之前工具會拒絕轉檔，並且說出要改哪個檔案。

### 移植腳本時發現腳本有個 bug

PowerShell 腳本寫 master playlist 時**永遠宣告 `CODECS="avc1.640028,mp4a.40.2"`**，
不管來源有沒有音軌。一份宣稱有音軌但實際沒有的 manifest，有些播放器會當成
「壞掉的串流」而不是「靜音的串流」。

新的版本會依 ffprobe 的結果決定，無音軌就只宣告視訊 codec，而且 ffmpeg 那邊也改成
`-an` 而不是指定一個不存在的音軌要用什麼編碼。

### 決策都在可測的地方

`shared/encodePlan.ts` 是純函式：畫質階梯、寬度、ffmpeg 參數、master playlist、
進度解析。`main/transcoder.ts` 只負責跑程序和把檔案放對位置 —— 那部分沒有測試會
講實話。

階梯跟後端的 `video.ladder_for` 逐一核對（2160／720／1000／320 四個邊界都一致）。
不一致的後果是產生出伺服器不肯簽的檔名。

進度解析吃 `-progress pipe:1` 的輸出，而不是刮人類可讀的 log —— 後者在不同 build
之間會變。順手處理了舊 build 用 `out_time_ms` 而新的用 `out_time_us`：
把毫秒當微秒讀，進度條會爬得像壞掉。

### 審查對照計畫抓到一個缺口

task 清單寫「顯示轉檔進度、**可取消**」，我第一版沒做取消。

轉檔是幾十分鐘的事，而「取消」如果只是停止顯示進度，機器還是會為了沒人要的輸出
佔著一顆核心半小時。現在取消會真的 kill ffmpeg，而且**被 kill 的程序 exit code
非零，所以要先辨認出取消、再讀 exit code**，不然它會被當成轉檔失敗來報。

### 兩個入口是刻意的

拖 MP4 → 轉檔再上傳。拖已轉好的資料夾 → 直接上傳。

第二個不是為了相容 —— 它是上傳路徑在轉檔器存在之前被驗證的方式，
而且它會一直是「重傳一份 encode 而不用再花一小時重轉」的辦法。

## 部署後才發現的：端到端測試沒有測到「端」

配對畫面在後台顯示了、工具跑起來了、輸入正確的碼 —— 回應是
**`Cross-site request rejected`**。

那不是配對失敗。是 Worker 的 CSRF 閘門，它要求非安全方法同時帶
`x-luma-app: 1` 和一個在 `ALLOWED_ORIGINS` 裡的 `Origin`。

**桌面工具不是瀏覽器，它沒有任何可以誠實聲稱的 origin。**

### 為什麼我的測試全綠

我寫的「端到端驗收」是在進程內組請求，而那個 helper 一直都塞
`{"Origin": ADMIN_ORIGIN, "x-luma-app": "1"}`。所以它證明了路由和 scope 是對的，
**卻沒有證明一個真的非瀏覽器客戶端連得上**。

這是「斷言在錯的地方」的另一種形狀：不是斷言的位置錯，是**輸入不是真的輸入**。
測試替客戶端補上了它不會送的 header。

### 修法不是教工具假冒 origin

第一個念頭是讓工具送 `Origin: https://admin.luma-studio.tw`。那是說謊，而且
**為了一個 CSRF 從來不針對的客戶端，去弱化每個真實瀏覽器的檢查**。

CSRF 能成立的原因是**瀏覽器會自動附上 cookie**。它附不了 `Authorization` header ——
設了就會觸發 preflight，而我們的 preflight 只宣告 `content-type, x-luma-app`。
所以帶 Bearer token 的請求**根本不可能是 CSRF**，而那個 header 本身就是
「呼叫端刻意送的」的證明。

所以：`carries_bearer_token()` 的請求豁免這道檢查。並且在
`ALLOWED_REQUEST_HEADERS` 上加了註解，因為那兩件事是綁在一起的 ——
哪天有人把 `Authorization` 加進允許清單，這個豁免就變成瀏覽器到得了的洞。

配對兌換那條沒有 token（那正是它存在的理由），所以走另一條路：
`router.serve(csrf_exempt=...)`，由**擁有那條路由的那個部署**明列。
一個自己猜要豁免哪些路徑的檢查是沒人能審的檢查。

突變驗證：把豁免改成「全部放行」，六個測試在三個檔案裡掛掉 —— cookie 的保護沒被牽連。

### S2 驗收

你要的那條路走通了，而且有測試：**沒有 session 的工具換到 token → 建 asset 200
→ 要 presign 200（URL 帶 X-Amz-Signature）→ 打訂單/顧客/儀表板/課程/影片列表/封存
一律 403。** 另外釘了兩條：偽造的 token 401，拿 playback token 來當桌面 token 也 401。

## R2 的 S3 憑證進去了

Admin Worker 上四個名字對上 `video_storage.py` 讀的四個：
`R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY` 是 secret，`COURSE_SOURCE_BUCKET`、

## 三件懸著的事，收掉兩件半

### 「可新增資料夾與檔案」拿掉了

原本 S5 有一項是「工具的 R2 瀏覽畫面可新增資料夾與檔案」。問過用途之後改成**唯讀** ——
要的只是「確認影片真的傳上去了」。

會問是因為它跟設計正面衝突：object key 由伺服器依允許清單產生，而**播放閘道用同一份
清單**決定哪些 key 可以被讀。為了讓人手動放檔案而放寬那份清單，會連帶放寬播放權限。
而且它想解的問題已經有解法：import 回報缺哪些物件，工具自己補傳那幾個。

猜的成本不是白做一個功能，是為了它鬆掉一道權限檢查。

### 那支 PowerShell 腳本刪了

`scripts/transcode-course-video.ps1` 在原生命令參數位置寫了 `-b:v $rung.Bitrate`，
PowerShell 不會展開，傳給 ffmpeg 的是字面的 `System.Collections.Hashtable.Bitrate`。
它從來沒跑成功過。工具的轉檔器已經更完整，所以刪掉而不是修 —— 留一支壞的沒人跑的腳本，
下一個看到的人會以為它可以用。

順手改掉三處提到它的註解，其中 `uploader.ts` 那段原本說「這就是腳本留著的理由」。

### `GET /tools/ffmpeg/{檔名}`

工具會去抓 `{admin API}/tools/ffmpeg/{檔名}` 下載釘死的 FFmpeg。**後端沒有那個路由。**
我寫了下載端沒寫供應端，鏡像建好也是 404。

補上了。幾個決定：

**檔名走 pattern 而不是清洗。** 清洗要窮舉每一種寫 `..` 的方式，pattern 只要描述
「一個檔名長什麼樣」：單一路徑段、開頭是可見字元、只收壓縮檔後綴。

**需要桌面 token。** bytes 是公開的 GPL build，不是機密 —— 擋的是流量。一個開放的
端點每次請求送二十 MB，就是別人的免費 CDN。加進 `_VIDEO_ROUTES`，因為它就是上傳
工作的一部分：工具手上有 MP4，缺的是編碼器。

**沒有 binding 時回 503 並說缺哪個。** 未設定的部署和空的鏡像從工具看起來一樣，
但只有一種是「上傳東西就好」。

**重用 `serve_r2_image`，並把它改名成 `serve_r2_object`。** 它已經做了讀物件、404、
nosniff、content-type 預設 octet-stream —— 我差點又寫一份。名字改掉是因為它現在也
服務 zip。

### `LUMA_FFMPEG_DIR`

S4 的驗收（拖 MP4 → ready）在鏡像存在之前跑不了。加一個環境變數指向機器上已有的
FFmpeg，今天就能驗完整條路。

兩道限制讓它可以留在程式裡：**打包後一律拒絕**（`app.isPackaged`），因為一個能用
環境變數指向任意編碼器的安裝版等於沒有釘死；**`PINNED.version` 一填上就照樣比版本**。
可設定的只有「去哪裡找」，雜湊和版本永遠不是。

`ffmpeg.exe`、`ffprobe.exe`、`LICENSE`。zip 而不是 gyan 給的 7z —— 解壓縮用的是
Windows 內建的 bsdtar，它讀 zip 不讀 7z。

**我的容量估計錯了，而且那是會壞的那種錯。** 我在註解裡寫「大約二十 MB」，實際 74 MB
（兩支 exe 各 99 MB 未壓縮）。而 `serve_r2_object` 是整個讀進記憶體的：R2 的
ArrayBuffer 一份，Python bytes 再一份，74 MB 變成大約 148 MB，Worker 的上限是 128 MB。

所以加了 `Ctx.stream`，把 R2 的 body 直接當成 Response body 傳出去 ——
`workers.Response` 的 `RESPONSE_ACCEPTED_TYPES` 收 `ReadableStream`，所以這是直通
而不是自己重寫一個串流。

有測試釘住，用一個 `arrayBuffer()` 會 raise 的假物件。突變驗證：把 buffering 版本
放回去，只有那一條掛掉 —— 其他每條都還是綠的，因為 buffering 版在功能上完全正確，
它只在正式環境、只在這條路線唯一存在的理由上失敗。

**第二個錯**：`licencePaths()` 算的是 `binDir/../LICENSE`，那是我在壓縮檔還是假設性的
時候寫的（假設 `ffmpeg-x/bin/*.exe` + `ffmpeg-x/LICENSE`）。實際打包出來 exe 和
LICENSE 同一層，所以改成 `binDir/LICENSE`。

## 原始碼那半：一個有記錄的決定，不是一個待辦

那顆「開啟原始碼所在資料夾」拿掉了，沒有東西取代它的功能 —— 取代它的是一句真話。

原因不是懶。GPL 的「提供對應原始碼」義務在 **conveying（散布給別人）** 時成立，
現在只有兩個擁有這個系統的管理員自己安裝，屬於內部使用，義務沒有觸發。而那顆按鈕
指向 `toolsDir()/ffmpeg-source.tar.xz` —— 工具永遠不會下載那個檔案，按了什麼都不會
發生。**一個假裝滿足了義務的控制項比沒有控制項糟**，因為它讓人以為這件事處理完了。

現在視窗裡是條款全文，加上一行「FFmpeg 8.1.2-essentials_build，gyan.dev 的 release
build，對應的 FFmpeg 原始碼為上游 commit 38b88335f9」。三句話全部可以查證。

順手清掉因此變成死碼的三樣東西：`app:revealSource` handler、preload 的 `revealSource`、
`licencePaths()`。

我原本寫「義務會在 S7 成立」，那是錯的 —— 我假設下載頁是公開的。它在管理後台後面，
收件人還是那兩個人，跟現在手動裝一份沒有差別。**觸發條件是收件人，不是階段。**

會觸發的是：安裝檔放到不需要登入就能拿的地方、給外包剪輯或任何不在管理員名單上的人、
把 repo 或安裝檔公開。這幾件寫進了 task.md 的 S7 段落，因為那是下一個會有人想到
「要不要放個下載連結」的地方。

真的發生時問題比「補一個 zip」大：我們交出去的是別人編譯的 build，對應原始碼指的是
那個 build 的全部來源，而 gyan 只公佈 FFmpeg 的 commit，不公佈 x264／x265 用的
revision。三條路（不散布 binary／盡力補／自己編）也寫在那裡了。

## 第一次真的拖 MP4 進去，抓到一個轉檔 bug

階梯全部轉完，掛在封面：

```
產生封面失敗：[vost#0:0/libwebp_anim @ ...] Terminating thread with
return code -12 (Cannot allocate memory)
```

`libwebp_anim` 是**動畫** webp 編碼器。`-frames:v 1` 一直都在，所以不是幀數問題 ——
是 ffmpeg 對 `.webp` 輸出**預設就挑動畫編碼器**，即使只要一幀。在你機器上用真的
ffmpeg 確認過：

```
Stream #0:0 -> #0:0 (h264 (native) -> webp (libwebp_anim))
```

動畫編碼器會為一整個序列配置記憶體。我用 12 秒的 testsrc 重現不出來（那支過了），
所以確切的觸發條件跟來源有關 —— 但**用動畫編碼器產一張靜態圖本身就是錯的**，
不需要先找到觸發條件才修。

加了 `-c:v libwebp`（靜態編碼器，明講不推論）和 `-an`（封面用不到音軌，而且把音軌
map 進 webp 是一整類不必存在的 muxer 抱怨）。用同一組參數對「有音軌的來源」實測過，
輸出是 1280x720 的靜態 webp。

有測試釘住 `-c:v libwebp` 在參數裡、`libwebp_anim` 不在。

順手兩個間距：`.alert` 原本 `margin: 0`（因為它一直待在有 gap 的 `.stack` 裡），
在上傳畫面直接貼著按鈕，所以改成有上邊距、並在 `.stack` 裡歸零免得算兩次。
影片名稱那個 `<label>` 不是 block 元素，label／input／button 全貼在一起，改用
配對畫面同一個 `.field`。

以及：多檔拖曳原本 `const [file] = [...files]` 取第一個、其餘丟掉 ——
拖五支課會上傳一支而畫面看起來成功。現在明說拒絕。

## 一個 exit code 0 的壞 encode

那個誤入 commit 的 `desktop/init.mp4` 不是垃圾，是證據。1.4 KB、270×480、h264+aac ——
**fMP4 的 init segment**，時間戳正好是拖影片那一刻。它掉在 `npm run dev` 的工作目錄，
不在畫質資料夾裡。

去看真正的輸出目錄，三個階梯都是 `playlist.m3u8` + `segment-000000.m4s`，**沒有
`init.mp4`**。沒有 init segment 的 fMP4 播不了，而 playlist 裡寫著它的名字。

### 為什麼

ffmpeg 決定 init segment 要寫哪裡的方式，是在 `-hls_segment_filename` 裡找 `/`。
`\` 對它不是分隔符，所以 `C:\encodes\a\720p\segment-%06d.m4s` 被判定為「沒有目錄」，
init.mp4 就落到工作目錄。

我第一次手動重現時**沒重現出來** —— 因為我在 bash 裡打的是 `/`。同一組參數只把分隔符
換成 `\`，init.mp4 就從目標資料夾跑到 cwd。這才是關鍵差異。

**而 ffmpeg 的 exit code 是 0。** 每一個階梯都「成功」，encode 是壞的。這就是為什麼它
一路跑到上傳才被發現。

修法是 `toFfmpegPath()`，套用在每一個路徑參數上而不是只套在 segment pattern —— 「哪些
參數需要」不該是任何人要記住的事。`-hls_fmp4_init_filename` 保持裸檔名，因為 ffmpeg
用同一個字串當「寫出的路徑」和「playlist 裡的 URI」，絕對路徑會進 manifest，播放閘道
會拒絕。

### 驗證方式

單元測試釘住字串。但字串不是出錯的地方 —— 出錯的是 ffmpeg 拿到字串之後的行為。所以另外
用真 binary、真 Windows 路徑跑了一次完整的三階梯 + 封面：

```
1080p: exit=0 init=true files=4
720p:  exit=0 init=true files=4
480p:  exit=0 init=true files=4
poster: exit=0 exists=true
```

突變驗證：把 `toFfmpegPath` 改成原樣回傳，同一支腳本回報三個 `init=false`，exit code
全部還是 0。

順手拿掉 `ffmpegArgs` 的 `outDir` 參數 —— 它是必填、從來沒被讀過，而且它的存在正好
暗示「init 的位置由 outDir 決定」，那就是讓這個 bug 通過的認知。

## S4 驗收：拖進 MP4 → ready，跑通了

在你不在的時候用一支無頭 harness 跑的：同一份 `out/main/index.js`、同一組 IPC，
少的只有拖曳這個動作，而 `upload:start` 不在意路徑怎麼來的。

過程中撞到三件事，兩個是我的 bug，一個是 harness 自己的。

### harness 讀錯 userData

`npx electron <script>` 沒有 package.json 可讀，`app.getName()` 是 `Electron`，
userData 就變成 `Roaming\Electron` —— 一個空目錄。`npm run dev` 讀得到 package.json，
所以是 `Roaming\luma-video-uploader`。我一開始以為 token 掉了，其實是問了錯的目錄。

**順帶發現 `npm run smoke` 也是這樣。** 它一直報 `paired=false`，那不是「沒配對」，
是它看的是另一個空目錄。斷言剛好也是「未配對畫面」，所以一直綠。

另外兩件：`requestSingleInstanceLock` 是以 userData 為鍵，所以你開著的 dev 視窗會讓
harness 一啟動就 `app.quit()` —— exit 0、零輸出。改成用獨立的 userData，把配對複製進去。
而複製 `pairing.bin` 不夠：Windows 上 `safeStorage` 不是直接 DPAPI，它產生隨機金鑰存在
userData 的 `Local State` 裡，只搬密文搬不動金鑰。

### import 永遠不可能成功

`register_verified_asset` 是純 `INSERT`。工具的流程是 create 拿到 id（才能簽上傳網址）
再 import 同一個 id，所以那一列早就在了 —— 撞主鍵，500。

**而它是在 14 個物件全部上傳完之後才失敗的**，最貴的位置。

`FakeDatabase` 沒有鍵也沒有約束，所以測試一路綠。改成常數 + 真 SQLite 測試，跟
`CONSUME_SQL` 一樣的做法。假的擋不住這個，也不可能找到它。

`byte_size` 和 `source_key` 刻意不在 update 清單裡：create 知道來源大小、import 不送，
列上去就是把真數字蓋成 0。

順帶把兩件本來各自是待辦的事一起解掉：重送 import 變成冪等（不是第二列），以及新的
encode version 會搬動 `active_encode_version`（S8 要的）。

### 傳了封面，資料庫卻說沒有

第一次成功的回報是「已驗證 **13** 個檔案」，但上傳了 14 個。差的那個是 `poster.webp` ——
沒有任何 playlist 指向它，所以照著 manifest 走永遠走不到。而 `REGISTER_SQL` 把
`poster_key` 寫成 NULL，於是影片庫會顯示不出縮圖，也沒有人報錯。

`verify_encode` 現在會主動 HEAD 它。找不到**不會**讓 import 失敗 —— 沒有縮圖的影片照樣
能播，為了一張圖擋掉整個 encode 是把外觀問題升級成上傳失敗。但有找到就會記下來。
再次 import 沒帶封面時用 `COALESCE` 保住原本記下的那個。

修完再跑一次：`已驗證 14 個檔案`。

### 續傳的 key 太嚴格

第二次跑我傳的是正斜線路徑，ledger 就沒接上，開了第二個 asset 重傳 14 個物件。
`C:\encodes\a` 和 `C:/encodes/a` 在 Windows 是同一個資料夾，卻是兩個字串。
`jobId` 現在正規化分隔符並轉小寫，而且搬到 `shared/resume.ts` —— 它本來在
`main/uploader.ts` 裡，那個檔案 import 了 electron 所以測不到，這是它一直沒有測試的原因。

## 鏡像下載那條也驗完了，代價是三個 Windows 路徑坑

清掉 `LUMA_FFMPEG_DIR`、用全新的 userData 跑，逼它真的去鏡像抓。連撞四次才通。

**一、雜湊 65 個字。** 貼進 `PINNED` 的值是 `fa fffff c`（五個 f），實際是四個 —— 複製時多了一個字。
`problemWith` 在下載之前就擋掉了，訊息是「SHA-256 尚未填寫或格式不對」。
**這正是那道檢查存在的理由**：格式不對當成「尚未設定」，不是「跳過檢查」。
現在有測試釘住長度，讓壞的貼上死在測試裡而不是死在 74 MB 之後。

**二、物件放在桶根目錄，程式找 `ffmpeg/` 前綴。** 回 404（不是 401/403 —— token 是通的）。
prefix 留著，因為那個桶之後還要放原始碼、安裝檔、updater metadata；用 wrangler 把物件放到
`ffmpeg/ffmpeg-8.1.2.zip`。

**三、`tar` 不是 bsdtar。** 下載和雜湊都過了，掛在解壓縮：`tar: Cannot connect to C: resolve failed`。
GNU tar 把 `C:\...` 讀成 `host:path`。我先以為是路徑格式問題，改成在目標目錄用相對檔名之後
變成 `This does not look like a tar archive` —— 才發現真正的原因：**PATH 上的 `tar` 是
Git for Windows 的 GNU tar，它根本不讀 zip**。改成指名 `%SystemRoot%\System32\tar.exe`。

那個註解原本寫「Windows 從 1809 就內建 bsdtar」—— 沒錯，但它不在 PATH 的第一位。
指名一支唯一平台上的工具，成本是零。

跑通的完整路徑：74 MB 下載 → SHA-256 → bsdtar 解壓 → ffprobe → 三個階梯 → 封面 →
master.m3u8 → 14 個 presigned PUT → 驗證 14 個 → `ready`。

順帶記下 `npm run smoke` 的 `paired=false` 是怎麼來的（`electron <script>` 沒有 package.json
可取名字，userData 是隔壁的空目錄），因為那個假設害我先去找不存在的 token bug。
不改它 —— 指向真的 store 會讓它跟執行中的 app 搶 single-instance lock，然後靜靜地 exit 0。

## S5.1：讓版本有名字

`video_encode_versions`（migration 0035）＋ `verify_encode` 順手記下容量 ＋ import 寫那一列。

先做這一步的理由是它是 S5 剩下全部的地基：影片庫要顯示版本、S6 要算容量與判斷孤兒，
都需要「版本」在 D1 裡是一列而不是一個隱含的數字。而它自己結束在一個能跑的狀態 ——
表建了、import 多寫一列，沒有任何畫面依賴它才成立。

### 設計文件說要存 `active`，我沒有存

`design.md` 原本寫這張表要記「是不是 active」。**那是一個會漂移的欄位**，而
`video_assets.active_encode_version` 已經是那個答案。這跟 Phase 0 決定不存「這是實體
還是數位商品」是同一個理由，只是後果更難看：這個欄位漂移的方式是後台請管理員刪掉
會員正在看的那一版。

改成用 join 推導，並且用一個測試把「這張表沒有 active 欄位」釘住 —— 不然下一個人
會照文件補上去。文件也改了，因為留著它就變成一個看起來沒做完的項目。

### 兩個 statement 之間沒有交易，所以順序是有意義的

import 現在寫兩次 D1：版本那一列，還有 asset 那一列（`REGISTER_SQL`）。這個 codebase
刻意不用 D1 的 batch（`shop.py` 裡寫過理由），所以中間失敗是一個真實的狀態。

我第一版寫的是「asset 先、版本後」。對抗性審查指出那個順序錯了：留下的是一個
`ready` 的 asset，它的 `active_encode_version` 指向一個沒有任何列描述的版本 ——
而那正是 S6 的孤兒盤點會判定「這些物件沒人要」的形狀，對象是會員正在看的檔案。

反過來的順序留下的是一列沒人指向的版本：總量高估一個 encode，下次 import 就蓋掉。
**兩個都是壞狀態，但只有一個會刪掉正在播的影片。** 換了順序，並且用一個測試釘住
`database.writes` 裡誰先誰後 —— 這種東西沒有測試撐著，下一個人整理程式時會照
「先建主體再建附屬」的直覺換回來。

### 為什麼版本的數字會被蓋掉，而 `poster_key` 不會

同一個 diff 裡有兩個 upsert，對「重新 import 時舊值該不該保留」給了相反的答案，
值得寫清楚：

- `poster_key` 用 `COALESCE` 保住。它是一個**活得比證據久的宣稱** —— 記過一次的縮圖
  照樣顯示得出來，為了一次不巧的 HEAD 把它清成 NULL 是白虧。
- `object_count`／`byte_size`／`has_poster` 直接蓋掉。它們是**對桶裡現況的測量**，
  而一個只會往上走的測量不是測量。儲存頁存在的目的就是告訴人現在到底有什麼。

`created_at` 不在 update 清單裡（保留第一次出現的時間，孤兒的年齡門檻和 rollback
期是從它算的），`verified_at` 才是會動的那個。

### `byteSize` 是下界，不是真相

這個數字是跟著 playlist 走出來的，所以它只包含**現在的 manifest 指到的物件**。
同一個版本原地重傳、而新的 playlist 指向不同的分段名時，舊的分段還在桶裡，
既沒被刪也沒被算進去。

而且那些物件對 S6 的孤兒盤點也是隱形的 —— 盤點的判斷是「這個 prefix 有沒有對應的
版本列」，有列就整個 prefix 算有主。**S6 要處理這件事**：盤點既然本來就要列桶，
就可以把列出來的 key 跟 manifest 走出來的那組比對，差集就是被取代的殘骸。
記在這裡，不然它會以「總量看起來比帳單小」的形式在幾個月後被發現。

### 突變驗證抓到我自己寫了兩層互相遮蔽的防護

審查指出重複的 playlist 行會讓物件數和容量都被算兩次（master 是工具手寫的，
而這個數字現在會被存起來加總）。我加了去重：一個 `counted` 集合，加上迴圈裡的
`continue`。

然後突變驗證**沒有殺掉測試** —— 把 `count()` 裡的去重拔掉，測試還是綠的，因為迴圈
那層還在。兩層防護一件事，任何一層被拔掉都不會有人發現。

它們其實有兩個不同的理由，所以留下兩層、補成兩條測試：`count()` 保的是數字，
迴圈的 `continue` 保的是**不要再打一次 R2**（playlist 是上傳來的檔案，一份把同一個
rendition 寫一千遍的 master 會變成一千次資料夾走訪）。現在拔掉任一層都會有它自己的
測試掛掉。

**這是突變驗證第一次抓到「測試沒問題、但防護是多餘的」這個形狀。** 之前抓到的都是
測試假通過。

### 抽掉一個已經咬過人一次的測試 helper

真 SQLite 的測試要把生產 SQL 的 `?N` 換成字面值，這個手法已經有三份（`CONSUME_SQL`、
`REGISTER_SQL`，加上這次的）。而 `REGISTER_SQL` 那份帶著一句註解警告
**`?10` 必須在 `?1` 之前替換**，否則 `?1` 會先吃掉 `?10` 的前半，留下一個游離的 `0`
—— 一個離被測目標兩步遠的語法錯誤。

抽成 `conftest.bind_literals(sql, *values)`，一律從最大的號碼往下替換，順手處理
`None → NULL` 和字串引號。理由不是「三份重複」，是**那個陷阱已經需要一句註解來提醒
下一個人**，而註解擋不住第四份。這跟先前決定不抽那個三份兩行的 flag 檢查不衝突：
那個沒有陷阱，這個有。
