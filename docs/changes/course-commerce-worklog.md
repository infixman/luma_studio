# 課程商城開發總覽

這份文件記錄整個開發過程：做了什麼、審查發現什麼、修了什麼、以及**我自己下的判斷**。
持續更新，不另開新檔。

寫給之後要看的人，所以用白話。技術細節在各 phase 的 `spec.md` / `design.md` 裡。

---

## 一句話說這個專案在做什麼

原本的商城只能賣「有庫存、要寄送」的實體商品。現在要能賣線上課程，還要能賣
「課程 + 材料包」這種混合商品。

難點不是多加一個商品類型，而是**同一個購物車、結帳、訂單流程要同時處理**
「要寄的」和「要開通的」兩種東西。

---

## 核心設計：四層拆開

```
商品 Product      → 只管展示（名稱、圖片、上不上架）
方案 Offer        → 只管定價（顧客實際買的單位）
內容 Component    → 只管「這個方案付款後給什麼」
交付目標          → 課程 Course（開通觀看）或 庫存品 InventoryItem（出貨）
```

### 為什麼不用「商品類型」欄位

最直覺的做法是加一個欄位寫「這是實體 / 數位 / 混合」。**沒有這樣做**，因為那個欄位會漂移：

管理員今天把材料包從方案裡拿掉，如果忘了同步改欄位，系統就會以為還要出貨。
兩邊不一致的後果是「把數位商品寄出去」或「把實體商品搞丟」。

所以「要不要配送」「有沒有含課程」全部是**當下從內容清單推導出來的**，不存在資料庫裡，
前端也不准提交這些值（提交了直接回 400，不是忽略 —— 忽略會讓呼叫端以為被採納了）。

### 為什麼庫存要獨立出來

原本庫存數字掛在「方案」上。一個材料包同時被三個課程方案使用時，
數字放在其中一個方案上，對另外兩個就是錯的。

所以庫存搬到獨立的「庫存品」，三個方案共用同一批數量。

## 已經定案的商業規則（2026-07-30）

這八項原本是待決策，現在都定了。每一項都直接影響程式怎麼寫：

| 議題 | 決定 | 白話 |
|---|---|---|
| 退款後還能看嗎 | 自動收回 | 全額退款會停掉觀看權，但不刪觀看進度和訂單紀錄 |
| 混合商品何時開課 | 付款後立刻 | 不用等材料包寄到 |
| 觀看期限怎麼算 | **從第一次觀看起算** | 不是從購買日起算 |
| 課程能買幾份 | 一份 | 已經擁有的課程不能再買 |
| 免運門檻怎麼算 | 只算要寄的部分 | 買課程不會把訂單推過免運門檻 |
| 純課程訂單狀態 | 開通成功就完成 | 沒有出貨流程 |
| 課程封存後 | 已購買的人繼續看 | 封存只擋新的販售 |
| 能不能送課程 | 可以 | 但不會產生一筆零元訂單 |

**「從第一次觀看起算」是最影響實作的一項。**
付款時只記「幾天」，不算到期日；要等會員真的按下播放才開始倒數。
理由：不然還在等材料包寄到的會員，觀看期限就先被消耗掉了。

## 我自己下的判斷（你可以推翻）

這些不是文件裡寫死的，是我在實作時遇到選擇、自己決定的。列出來給你檢查。

### 1. 庫存品的編號沿用方案編號

搬移舊資料時，每個方案會生出一筆對應的「庫存品」。這筆庫存品的編號我直接沿用方案的編號。

- **好處**：搬移程式可以重複執行不出錯、不需要額外的對照表、日後查資料一眼看得出來源
- **代價**：兩張表裡有一樣的編號，看 log 時要多想一秒

你在 7/30 確認「維持」。

### 2. 草稿課程可以先加進方案，但方案不能上架

原本可以設計成「課程沒發布就不准加進方案」。**沒有這樣做**，因為那會強迫管理員
一定要先把課程做完才能建商品。

改成：加的時候放行，但方案要啟用時會擋下來，並明確說「課程 X 尚未發布」。

### 3. 商品編輯頁的庫存欄位，共用的庫存品不給改

商品編輯頁上那個「庫存」欄位，只有在該方案剛好對應唯一一個、且沒有被別人共用的
庫存品時才能改。

其他情況直接拒絕並說「請到庫存品管理調整」。因為共用的數量屬於所有使用它的方案，
從某個商品頁改掉會靜默影響其他商品。

### 4. `variant.stock` 這個舊欄位還留著，而且還在寫

理想上庫存只該有一個來源。但訂單的扣庫存要到 Phase 3 才搬完，現在拿掉舊欄位
會讓商城賣出不存在的庫存。

所以舊欄位降級成「鏡像」，只由**一個函式**寫入，Phase 7 清理時只要刪那一行。
已記錄在 Phase 2 的 task 文件裡，不是漏掉。

### 5. 前端測試環境選了 happy-dom，沒裝 testing-library

專案原本沒有能渲染畫面的測試。加了 `happy-dom`（一個 devDep），
用 Preact 自己的 render + 原生 DOM 查詢，沒有引入 testing-library。

理由：這個專案相依很精簡，能用內建的就不多加一層。

### 6. 舊購物車格式的相容期訂為「兩個前端版本 + 90 天」

購物車存在瀏覽器裡而且**沒有過期時間**，久沒回訪的顧客可能還存著幾個月前的舊格式。
縮短這個數字等於選擇讓那些人的購物車靜默清空。

### 7. 重複購買鎖放在 Phase 3 而不是 Phase 2

「不能重複購買已擁有的課程」需要一張鎖表。我把它放在 Phase 3（結帳併發保護），
不是 Phase 2（建表）。也可以主張跟其他新表一起建。

## 過程中找到的真實 bug

都是**先寫測試讓它失敗，再修**。這樣才知道測試真的抓得到。

| # | Bug | 影響 | 怎麼發現的 |
|---|---|---|---|
| 1 | `update_variant` 少傳一個參數 | 商品編輯頁儲存售價庫存**直接壞掉** | Phase 2 接線時發現 |
| 2 | 上架中卻沒有可販售方案的商品沒人管 | 顧客看得到、買不了 | 盤點 Phase 1 缺口時 |
| 3 | 庫存品搜尋有競態 | 打字快時會顯示錯誤的搜尋結果 | 審查指出 |
| 4 | 內容數量每按一鍵就存一次 | 打「12」會先送 1；清空欄位會送 NaN | 審查指出 |
| 5 | 警告訊息的 key 重複 | 三門未發布課程會產生重複 key | 審查指出 |
| 6 | **純文字單元跳過了權限檢查** | 沒買課程的人可以對它寫觀看進度，而且進度算在他宣稱的任何課程上 | 最終審查指出 |
| 7 | **後端做完了、前端沒接** ×4 | 見下方「四個斷點」——功能實際上跑不起來 | 完工後自我盤點 |

**第 1 個最值得說**：Phase 1 的工作清單把「更新單一商品時同步更新方案」打勾了，
但沒有測試涵蓋，所以這個一定會爆的錯放到現在才被發現。

**第 6 個是最危險的**：判斷「這個單元能不能播」時，我把「有沒有影片」的檢查
寫在「有沒有買」的**前面**。結果純文字單元對所有人都回答「沒有影片」——
包括沒買課程的人。而上層又把「沒有影片」當成無害（因為閱讀單元本來就該能標記完成），
於是就變成：沒買課程的人可以寫進度，而且課程 ID 是他自己送的。

檢查順序調換就修好了。教訓是**授權檢查要放在所有其他判斷之前**，
不然任何一個「無害的提前返回」都可能變成一個洞。

## 審查建議我沒有採納的

### 「`_component_view` 重複查詢，拿掉省一次」

拿掉會製造 bug。

`resolve_offer` 會**故意丟棄**「目標已封存」的內容 —— 購物車不能報價出貨不了的東西。
但編輯器正是拿來移除那個壞掉內容的畫面，它不能移除自己沒被顯示的東西。

已在程式碼註解寫清楚，免得下次有人又想「優化」掉。

### 「useEffect 缺少 cleanup」

Preact 不像 React 會對此發出警告，而且這些頁面只在掛載時載入一次。
真正會出問題的情境（較慢的舊請求蓋掉新結果）已經在第 3 項單獨修掉了。

## 目前的測試狀況

- 後端：全綠
- 前端：39 個檔案、374 個測試，全綠
- 型別檢查：乾淨

新增的測試裡有幾類特別值得留著：

- **真 SQLite 跑整份 migration**。之前只檢查 SQL 字串長得對不對，那連「這句 SQL 資料庫肯不肯收」都測不出來。改用真的 SQLite 之後，第一次跑就抓到我把欄位名稱猜錯了。
- **突變驗證**。新寫的測試我會故意把程式改壞，確認測試真的會紅，再改回來。不然可能寫出一個永遠會過的空測試。

## Phase 3：購物車、結帳、訂單、開通

已完成：
- 資料表（訂單交付快照、會員權限、權限來源、重複購買鎖）
- 權限授予與撤銷的邏輯（可重複執行，付款通知重送不會出問題）
- 購物車改走統一的展開邏輯，純課程不問配送
- 訂單建立改扣庫存品、寫交付快照
- 結帳 API 條件式欄位：**先算價，再決定要哪些欄位**。純課程不要配送方式、不要電話、不要地址；姓名還是要（收據和通知信要用）
- 付款後開通：`provision_paid_order`

- 訂單頁分開顯示「數位內容」和「待出貨內容」（顧客端與後台都做了）
- 純數位訂單不能被標記出貨（後端擋 + 後台不顯示按鈕）

- 重複購買鎖串接完成

待做：
- 退款撤銷的管理介面（Phase 7）

### 為什麼需要「重複購買鎖」

購物車會說「你已經擁有這門課」，但**購物車是一個畫面，不是保證**。
開兩個分頁、或在慢速網路下連點兩次，兩邊都會在訂單成立前通過那個檢查。

所以結帳時要先搶一把鎖（同一個會員 + 同一個方案只能有一把）。搶不到的那筆直接被擋下。

三個細節：

- **鎖在扣庫存之前搶**。要把人擋下來，就在還沒為他從架上拿走任何東西之前擋。
- **過期的鎖可以被接管**。有人結帳到一半跑掉，不能讓他從此再也買不了這門課。
- **付款後鎖不再過期**。已付款的鎖要留著，否則十五分鐘後同一個人又能再買一次。

### 訂單頁為什麼要分區

課程在付款當下就能看，材料包不能。混在同一張清單裡，整筆訂單看起來都還在路上，
已經拿到觀看權的會員會去找一個不存在的物流單號。

所以分成「數位內容 / 已開通」和「待出貨內容」兩區。純數位訂單連「收件資料」卡片都不顯示
—— 一整張空欄位看起來像資料遺失。

### 一個防呆的預設值選擇

後台的「標記已出貨」按鈕，在拿不到 `hasPhysical` 這個欄位時**仍然顯示**。

看起來不安全，但反過來想：這種情況只會發生在「後台比 API 新」的時候，
而部署順序是後端先上，所以那代表發生了回滾。這時候把按鈕藏起來，
真正有包裹要寄的訂單就出不了貨。顯示它最多換來一個伺服器本來就會回的錯誤。

已抽成 `shippableMoves` 並用測試把三種情況都釘住。

### 付款後開通的一個關鍵細節

`provision_paid_order` 的呼叫**故意放在「狀態真的改變了」的判斷之外**。

如果放在裡面：第一次付款通知進來，狀態改成已付款，但開通課程時失敗了。
第二次通知進來，發現訂單已經是已付款，於是跳過整段 —— 這個會員就永遠拿不到課程。

放在外面，每次通知都會嘗試補開通，已經開通過的會被 SQL 條件擋掉。

### 純數位訂單會自己完成

沒有包裹要寄，就沒有人會去把它從「已付款」推到「已完成」。所以開通全部成功後自動轉完成。

但**只有在全部成功之後**。開通失敗卻標成已完成，等於用一個綠勾把問題蓋住。

## Phase 4：影片上傳與轉檔

### 決策變更（2026-07-30）：不用 Cloudflare Container

原計畫是自建轉檔管線 —— 一個 TypeScript 媒體 Worker、Queue、跑 FFmpeg 的 Container。
你決定不承擔它的持續費用與運維面積。

改成：**本機轉檔 → 同步到 R2 → 一支端點驗證後註冊。**

| 原設計 | 實際 |
|---|---|
| Container 跑 FFmpeg | `scripts/transcode-course-video.ps1` 在本機跑 |
| Queue 排程與重試 | 不需要；轉檔失敗就在本機重跑 |
| 瀏覽器 multipart 直傳 | rclone 同步 |
| Media Control Worker（TypeScript） | 不需要；沒有 SigV4 簽章需求了 |

**這個改變讓最不確定的技術風險消失了。** Phase 4 原本提議多開一個 TypeScript Worker，
唯一理由是「Python Worker 能不能乾淨地做 AWS SigV4 簽章」沒人驗證過。
不做瀏覽器直傳，就不需要簽章，那個問題直接不存在。

### 驗證變得更重要，不是更不重要

手動同步幾百個檔案，**少傳一個是常態**。而少一個分段的影片會播到那一段才斷 ——
這是最糟的發現時機。

所以 `video.verify_encode` 會讀 master playlist、逐一確認每個被引用的物件真的存在，
**一次回報所有缺漏**（讓你重跑一次同步，而不是重跑六次）。

三個容易漏掉的檢查點：

- **init segment 藏在 `EXT-X-MAP` 標籤裡**，不在自己的一行。播放器有全部分段卻少了它，
  一段都解不出來 —— 很容易從檢查清單裡漏掉，而代價很高。
- **不是 playlist 的檔案回傳空清單**，而不是回傳它的每一行。呼叫端會把每一行當成路徑去抓。
- **`../` 直接拒絕。** playlist 是別人上傳的檔案，跟著它跳出自己的資料夾，
  等於讓一次上傳決定驗證器（以後還有閘道）去讀 bucket 裡的什麼。

### 保留下來的東西

資料表、物件路徑、狀態機、畫質階梯、播放閘道都照原設計實作，沒有改。
日後想自動化轉檔，這些都還在，只需要補上排程與執行環境。

註冊端點寫進 `ready` 是**唯一繞過狀態機的地方** —— 這個資產沒有上傳工作階段、
沒有轉檔工作，所以沒有更早的狀態可以來自。而且只在驗證通過之後。

### 還沒做

影片庫的畫面（列表與封存的 API 都完成了）。真實媒體檔的 fixture 測試
（直式、無音軌、可變幀率、損壞檔）需要實際檔案。

## Phase 5：課程編輯

不需要新資源，所以完整做了後端。

### 已完成

- 課程展示欄位（簡介、封面、講師、難度、語言、適合對象、學習成果…）
- 章節與單元
- 大綱驗證、發布檢查、公開資料形狀
- 管理 API：大綱讀寫、發布、封存

### 幾個刻意的決定

**單元不存影片長度。** 長度屬於影片本身，抄一份在這裡的話，影片一重新轉檔就錯了。

**大綱是整棵樹一起驗證、一起替換。** 替換等於先刪掉舊的，如果驗證到一半才發現某個單元
有問題，課程會少掉一半章節而且沒東西可以放回去。

**排序用「送過來的順序」，不用前端給的數字。** 前端會送重複的、跳號的、99 的，
它真正的意思是「這個順序」。

**發布檢查一次回報全部問題。** 每存一次只知道一個問題、修完才發現下一個，是很糟的下午。

**沒有影片的單元可以發布。** 純文字的閱讀單元是合理的。但「指定了影片、而影片還在轉檔」
會被擋下 —— 那等於賣一個轉圈圈的載入畫面。

**公開資料會列出每個單元的名稱，但只有試看單元附內容。** 知道課程教什麼正是商品頁的用途；
其餘是付費才有的。而且**沒有任何單元會帶影片的 ID** —— ID 是可以拿去找東西的，
播放權要靠 Phase 6 的閘道驗證，不能靠「知道名字」。

**`published_at` 只記第一次。** 編輯後重新發布不是一門新課程，覆蓋掉會失去「什麼時候真正上架」。

## Phase 6：會員觀看與播放授權

### 核心取捨：只在發播放權時查一次資料庫

一堂課會產生**幾百次**影片分段請求。如果每次都去查「這個人買了嗎」，
成本會高過它保護的東西。

所以改成：建立播放 session 時查一次，然後發一張**短效簽章 token**。
之後每個分段只驗簽章，不碰資料庫。

代價是「取消觀看權」不會立刻生效，要等目前這張 token 過期（十五分鐘內）。
這是刻意的取捨，不是疏漏。

### Token 的設計重點都是無聊的那些

- **寫明它開的是哪一支影片、哪一個轉檔版本** —— 一堂課的 token 不能打開整門課，
  舊版的 token 也不能碰新版
- **會過期**，而且「從未來簽發的」直接拒絕（時鐘誤差很小，來自未來的 token 不是誤差）
- **常數時間比對** —— 一個遇到第一個錯字元就停的比較，會告訴攻擊者他猜對了多少，
  一次一個請求
- **驗證時接受前一把金鑰，簽發只用現在這把** —— 換金鑰不能讓所有會員在課上到一半被登出
- **失敗一律回 None** —— 「過期」和「偽造」對正在試探的人來說是同一個答案，
  差別記在 log 裡

### 路徑用白名單，不用黑名單

只接受轉檔程式實際會產生的那幾種檔名。每一份「traversal 手法清單」都會漏掉一種，
而這些檔名完全可預測，沒有理由接受別的。

### 觀看期限在這裡才開始算

付款時只記「幾天」。真正開始倒數是在**第一次成功取得播放權**的時候，
用一個帶條件的 UPDATE（`first_viewed_at IS NULL`）保證只成功一次。

沒有這個條件的話，每按一次播放都會重設，三十天的課程就變成永久的了。

### 這不是 DRM

能看的人可以錄下他看到的東西。目標是「不能看的人看不到」，
以及「脫離情境被分享出去的網址會很快失效」。文件裡明白寫出來，不誇大。

## Phase 7：營運工具

### 對帳查詢：專門找「應該發生卻沒發生」的事

每一支查詢都對應一種會靜默發生的失敗：

| 找什麼 | 為什麼重要 |
|---|---|
| 已付款但課程沒開通 | 顧客**立刻就會感覺到**，而且他自己無能為力 |
| 逾期卻還佔著庫存 | 定時工作漏掉的那些（部署中斷、isolate 死掉） |
| 卡住的轉檔工作 | Container 死掉會讓那個版本永遠鎖住，重試也進不來 |
| 所有來源都撤銷了、權限卻還在 | **有人在看一門已經退費的課**，正常流程永遠不會發現 |
| 孤兒的購買鎖 | 會員被告知「你已經擁有」一個他其實沒有的東西 |

**這些查詢只找，不修。** 修的工作交給本來就知道怎麼修的程式碼
（`provision_paid_order`、`release_stock`）。同一個修復寫兩遍，就會有兩種行為。

查詢範圍也刻意窄。一支會回傳全部東西的掃描，是沒有人敢按的掃描。

### 功能開關放在伺服器

前端可以用開關決定要不要畫按鈕，但**後端用它決定要不要允許**。
「把按鈕藏起來」從來沒有阻止過任何人直接呼叫底下那支 API，而那支 API 才是收錢的。

兩個細節：

- **沒設定就是關閉**。沒有被告知要賣課程的部署，不該因為少一個變數就開始賣。
- **只有 `"1"` 算開啟**。也接受 "true" 的話會變成兩種拼法、然後三種，
  最後有一種在關鍵時刻默默失效。

### 退款：部分退款一定要指名

全額退款會撤銷這張訂單給出的所有課程。部分退款**必須明確指出撤銷哪幾筆** ——
從退款金額反推「他該失去哪一門課」是在猜，而被猜的東西是某個人的觀看權。

送了空清單的部分退款直接拒絕，不是默默什麼都不做。

## 課程編輯器

之前只能看不能改，所以**實際上沒辦法建立一門課**。現在可以了。

### 大綱編輯

章節與單元都能新增、移除、上下移動。影片從已完成轉檔的清單裡選，也可以不選（純文字單元）。

三個實作上的決定：

**整棵樹一起送。** 伺服器是整組替換的，所以編輯器持有一份草稿、由頁面一次存。
每一列各自存的話，任何一次失敗都會留下改一半的大綱 —— 半門課比沒存還糟。

**每次變動都重新編號。** `position` 是伺服器排序的依據，只調整陣列順序而不重新編號，
存下去會是作者原本的順序。

**只列出轉檔完成的影片。** 指向還在轉檔的影片無法發布，在這裡提供它只會在稍後產生一個錯誤。

**移除章節會說「裡面的 N 個單元會一起移除」。** 這件事不明顯，而且無法還原。

### 長文欄位

「你將學會 / 適合對象 / 課程介紹 / 先備知識 / 需要準備的工具 / 講師介紹」六個欄位
用既有的 rich text editor。順序照著「一個正在決定要不要買的人」閱讀的順序排。

HTML 一律在後端清理。有一個測試特別驗證**六個欄位都經過同一道門** ——
漏掉其中一個正是不會被發現的那種失誤。

### 未儲存警告

離開時會確認。因為未存的不只是一個欄位，是整份大綱。

### 一個測試上的教訓

我原本寫「檢查回傳的 HTML 沒有 script」，但假資料庫回傳的是原始 fixture 不是寫入值，
所以那個測試**通過但什麼都沒驗到**。改成直接測「路由組出來的東西」而不是「讀回來的東西」。

這是這個專案裡第三個假通過的測試了。共同點都是：斷言的對象不是實際發生變化的地方。

## 給之後的人：幾個容易誤解的地方

1. **「方案」和「規格」是同一件事的兩個名字**。程式裡舊的叫 `variant`，新的叫 `offer`，值是一樣的。
2. **觀看期限不是從購買算**。文案一律寫「觀看後 N 天」，不要寫成「購買後 N 天」，那是不同的商品。
3. **一個會員一門課只有一筆權限，但可以有多個「來源」**。買兩次同一門課 = 一筆權限 + 兩個來源。退掉其中一次只會撤掉那個來源，權限還在。這是退款不會誤傷的關鍵。
4. **`expires_at` 是 NULL 有兩種意思**：永久，或是有期限但還沒開始看。兩種都算有效。

## 四個斷點：後端做完了、前端沒接

這是最值得記下來的一類問題：每一項的伺服器端都寫好也測過了，但**從瀏覽器碰不到**。
測試全綠，功能不能用。

### 1. 結帳頁還在要求電話與地址

後端已經改成「純課程不要求配送方式、電話、地址」，前端沒跟上。
買課程的顧客會停在一張問他「要寄到哪裡」的表單前，而且送出鍵在選了配送方式之前是停用的
—— 純數位購物車永遠不會被提供配送方式，所以那個鍵永遠按不下去。

現在請求只帶這筆訂單真正有的欄位。

### 2. 播放器只有 Safari 能用

`<video src="....m3u8">` 在 Safari 可以播，Chrome 和 Firefox 不行 ——
而且失敗的方式是「永遠不出現畫面」，看起來像影片壞掉而不是缺少解碼器。

改用 hls.js，而且是**按需載入**不打包進商城：大部分造訪是在購物不是在看課。

### 3. 學習頁完全沒有存進度

後端有 API，前端沒呼叫。所以「繼續上課」永遠回到第一課，完成數字永遠是 0。

寫入節流到 20 秒 —— `timeupdate` 一秒觸發好幾次，而這是只會被讀一次的資訊。
但**大幅往前拉會立刻寫入**：他已經移動了，等 20 秒的話關掉分頁就丟了。
失敗刻意吞掉：掉一次進度是倒退 20 秒，在正在播放的影片上蓋一個錯誤橫幅是失去這堂課。

### 4. 商品頁完全沒有課程資訊

公開 API 也沒回。顧客在商品頁看不到大綱、講師、時數。

課程會**跨方案去重** —— 「線上版」和「課程＋材料包」通常給同一門課，
列兩次會讀成兩門不同的課。每個單元都列出名稱（知道教什麼正是這一頁的用途），
只有試看單元附內容。純實體商品完全不查這些。

### 教訓

「後端測試全綠」和「使用者能用」是兩件事。每一個階段結束時應該問的是
**「現在有人能從瀏覽器走完這件事嗎」**，而不是「測試過了嗎」。

## 補完的五個較小項目

| 項目 | 做法 |
|---|---|
| 庫存調整稽核 | 新增 `inventory_audit_log`，記錄操作人、原因、前後數字。**數字沒變也記** —— 「我盤過了，是對的」正是日後發現不對時最想看到的那一筆。訂單扣庫存**不記**：系統在做它的工作不是誰要辯護的宣稱，每筆銷售一行會把真正重要的埋掉 |
| 圖片來源限制 | 只接受本站自己的資源路徑。特別擋掉 `//host/x.gif` —— 它會繼承頁面的協定去別人家抓東西，而且很容易看漏 |
| 外部連結 rel | http(s) 連結自動加 `noopener noreferrer`，**取代**而非附加作者寫的值。`mailto:` 和 `tel:` 不加，它們沒有開新分頁 |
| 播放閘道快取 | 分段是不可變的（重新轉檔就是新版本、新路徑），所以可以放邊緣快取。**授權在查快取之前** —— 快取鍵刻意不帶身分，這讓它可以共用，也讓順序變得重要 |
| 影片資產管理 API | 列表、封存、引用查詢。封存前檢查有沒有單元在用，有就拒絕並說出單元名稱 —— 讓管理員被擋下來，比讓會員發現看不了好 |

一個行為變更值得注意：**既有頁面裡指向外部網址的圖片會被清掉。**
專案有媒體庫與選擇器，所以實際內容應該都用內部路徑，但這是我改的東西裡唯一會動到既有資料呈現的一項。
