# 課程商城開發總覽

這份文件記錄整個開發過程：做了什麼、審查發現什麼、修了什麼、以及**我自己下的判斷**。
持續更新，不另開新檔。

寫給之後要看的人，所以用白話。技術細節在各 phase 的 `spec.md` / `design.md` 裡。

---

## 一句話說這個專案在做什麼

原本的商城只能賣「有庫存、要寄送」的實體商品。現在要能賣線上課程，還要能賣
「課程 + 材料包」這種混合商品。

難點不是多加一個商品類型，而是**同一個購物車、結帳、訂單流程要同時處理**
「要寄的」和「要開通的」兩種東西。

---

## 核心設計：四層拆開

```
商品 Product      → 只管展示（名稱、圖片、上不上架）
方案 Offer        → 只管定價（顧客實際買的單位）
內容 Component    → 只管「這個方案付款後給什麼」
交付目標          → 課程 Course（開通觀看）或 庫存品 InventoryItem（出貨）
```

### 為什麼不用「商品類型」欄位

最直覺的做法是加一個欄位寫「這是實體 / 數位 / 混合」。**沒有這樣做**，因為那個欄位會漂移：

管理員今天把材料包從方案裡拿掉，如果忘了同步改欄位，系統就會以為還要出貨。
兩邊不一致的後果是「把數位商品寄出去」或「把實體商品搞丟」。

所以「要不要配送」「有沒有含課程」全部是**當下從內容清單推導出來的**，不存在資料庫裡，
前端也不准提交這些值（提交了直接回 400，不是忽略 —— 忽略會讓呼叫端以為被採納了）。

### 為什麼庫存要獨立出來

原本庫存數字掛在「方案」上。一個材料包同時被三個課程方案使用時，
數字放在其中一個方案上，對另外兩個就是錯的。

所以庫存搬到獨立的「庫存品」，三個方案共用同一批數量。

## 已經定案的商業規則（2026-07-30）

這八項原本是待決策，現在都定了。每一項都直接影響程式怎麼寫：

| 議題 | 決定 | 白話 |
|---|---|---|
| 退款後還能看嗎 | 自動收回 | 全額退款會停掉觀看權，但不刪觀看進度和訂單紀錄 |
| 混合商品何時開課 | 付款後立刻 | 不用等材料包寄到 |
| 觀看期限怎麼算 | **從第一次觀看起算** | 不是從購買日起算 |
| 課程能買幾份 | 一份 | 已經擁有的課程不能再買 |
| 免運門檻怎麼算 | 只算要寄的部分 | 買課程不會把訂單推過免運門檻 |
| 純課程訂單狀態 | 開通成功就完成 | 沒有出貨流程 |
| 課程封存後 | 已購買的人繼續看 | 封存只擋新的販售 |
| 能不能送課程 | 可以 | 但不會產生一筆零元訂單 |

**「從第一次觀看起算」是最影響實作的一項。**
付款時只記「幾天」，不算到期日；要等會員真的按下播放才開始倒數。
理由：不然還在等材料包寄到的會員，觀看期限就先被消耗掉了。

## 我自己下的判斷（你可以推翻）

這些不是文件裡寫死的，是我在實作時遇到選擇、自己決定的。列出來給你檢查。

### 1. 庫存品的編號沿用方案編號

搬移舊資料時，每個方案會生出一筆對應的「庫存品」。這筆庫存品的編號我直接沿用方案的編號。

- **好處**：搬移程式可以重複執行不出錯、不需要額外的對照表、日後查資料一眼看得出來源
- **代價**：兩張表裡有一樣的編號，看 log 時要多想一秒

你在 7/30 確認「維持」。

### 2. 草稿課程可以先加進方案，但方案不能上架

原本可以設計成「課程沒發布就不准加進方案」。**沒有這樣做**，因為那會強迫管理員
一定要先把課程做完才能建商品。

改成：加的時候放行，但方案要啟用時會擋下來，並明確說「課程 X 尚未發布」。

### 3. 商品編輯頁的庫存欄位，共用的庫存品不給改

商品編輯頁上那個「庫存」欄位，只有在該方案剛好對應唯一一個、且沒有被別人共用的
庫存品時才能改。

其他情況直接拒絕並說「請到庫存品管理調整」。因為共用的數量屬於所有使用它的方案，
從某個商品頁改掉會靜默影響其他商品。

### 4. `variant.stock` 這個舊欄位還留著，而且還在寫

理想上庫存只該有一個來源。但訂單的扣庫存要到 Phase 3 才搬完，現在拿掉舊欄位
會讓商城賣出不存在的庫存。

所以舊欄位降級成「鏡像」，只由**一個函式**寫入，Phase 7 清理時只要刪那一行。
已記錄在 Phase 2 的 task 文件裡，不是漏掉。

### 5. 前端測試環境選了 happy-dom，沒裝 testing-library

專案原本沒有能渲染畫面的測試。加了 `happy-dom`（一個 devDep），
用 Preact 自己的 render + 原生 DOM 查詢，沒有引入 testing-library。

理由：這個專案相依很精簡，能用內建的就不多加一層。

### 6. 舊購物車格式的相容期訂為「兩個前端版本 + 90 天」

購物車存在瀏覽器裡而且**沒有過期時間**，久沒回訪的顧客可能還存著幾個月前的舊格式。
縮短這個數字等於選擇讓那些人的購物車靜默清空。

### 7. 重複購買鎖放在 Phase 3 而不是 Phase 2

「不能重複購買已擁有的課程」需要一張鎖表。我把它放在 Phase 3（結帳併發保護），
不是 Phase 2（建表）。也可以主張跟其他新表一起建。

## 過程中找到的真實 bug

都是**先寫測試讓它失敗，再修**。這樣才知道測試真的抓得到。

| # | Bug | 影響 | 怎麼發現的 |
|---|---|---|---|
| 1 | `update_variant` 少傳一個參數 | 商品編輯頁儲存售價庫存**直接壞掉** | Phase 2 接線時發現 |
| 2 | 上架中卻沒有可販售方案的商品沒人管 | 顧客看得到、買不了 | 盤點 Phase 1 缺口時 |
| 3 | 庫存品搜尋有競態 | 打字快時會顯示錯誤的搜尋結果 | 審查指出 |
| 4 | 內容數量每按一鍵就存一次 | 打「12」會先送 1；清空欄位會送 NaN | 審查指出 |
| 5 | 警告訊息的 key 重複 | 三門未發布課程會產生重複 key | 審查指出 |

**第 1 個最值得說**：Phase 1 的工作清單把「更新單一商品時同步更新方案」打勾了，
但沒有測試涵蓋，所以這個一定會爆的錯放到現在才被發現。

## 審查建議我沒有採納的

### 「`_component_view` 重複查詢，拿掉省一次」

拿掉會製造 bug。

`resolve_offer` 會**故意丟棄**「目標已封存」的內容 —— 購物車不能報價出貨不了的東西。
但編輯器正是拿來移除那個壞掉內容的畫面，它不能移除自己沒被顯示的東西。

已在程式碼註解寫清楚，免得下次有人又想「優化」掉。

### 「useEffect 缺少 cleanup」

Preact 不像 React 會對此發出警告，而且這些頁面只在掛載時載入一次。
真正會出問題的情境（較慢的舊請求蓋掉新結果）已經在第 3 項單獨修掉了。

## 目前的測試狀況

- 後端：全綠
- 前端：31 個檔案、323 個測試，全綠
- 型別檢查：乾淨

新增的測試裡有幾類特別值得留著：

- **真 SQLite 跑整份 migration**。之前只檢查 SQL 字串長得對不對，那連「這句 SQL 資料庫肯不肯收」都測不出來。改用真的 SQLite 之後，第一次跑就抓到我把欄位名稱猜錯了。
- **突變驗證**。新寫的測試我會故意把程式改壞，確認測試真的會紅，再改回來。不然可能寫出一個永遠會過的空測試。

## 給之後的人：幾個容易誤解的地方

1. **「方案」和「規格」是同一件事的兩個名字**。程式裡舊的叫 `variant`，新的叫 `offer`，值是一樣的。
2. **觀看期限不是從購買算**。文案一律寫「觀看後 N 天」，不要寫成「購買後 N 天」，那是不同的商品。
3. **一個會員一門課只有一筆權限，但可以有多個「來源」**。買兩次同一門課 = 一筆權限 + 兩個來源。退掉其中一次只會撤掉那個來源，權限還在。這是退款不會誤傷的關鍵。
4. **`expires_at` 是 NULL 有兩種意思**：永久，或是有期限但還沒開始看。兩種都算有效。

### 為什麼需要「重複購買鎖」

購物車會說「你已經擁有這門課」，但**購物車是一個畫面，不是保證**。
開兩個分頁、或在慢速網路下連點兩次，兩邊都會在訂單成立前通過那個檢查。

所以結帳時要先搶一把鎖（同一個會員 + 同一個方案只能有一把）。搶不到的那筆直接被擋下。

三個細節：

- **鎖在扣庫存之前搶**。要把人擋下來，就在還沒為他從架上拿走任何東西之前擋。
- **過期的鎖可以被接管**。有人結帳到一半跑掉，不能讓他從此再也買不了這門課。
- **付款後鎖不再過期**。已付款的鎖要留著，否則十五分鐘後同一個人又能再買一次。

### 訂單頁為什麼要分區

課程在付款當下就能看，材料包不能。混在同一張清單裡，整筆訂單看起來都還在路上，
已經拿到觀看權的會員會去找一個不存在的物流單號。

所以分成「數位內容 / 已開通」和「待出貨內容」兩區。純數位訂單連「收件資料」卡片都不顯示
—— 一整張空欄位看起來像資料遺失。

### 一個防呆的預設值選擇

後台的「標記已出貨」按鈕，在拿不到 `hasPhysical` 這個欄位時**仍然顯示**。

看起來不安全，但反過來想：這種情況只會發生在「後台比 API 新」的時候，
而部署順序是後端先上，所以那代表發生了回滾。這時候把按鈕藏起來，
真正有包裹要寄的訂單就出不了貨。顯示它最多換來一個伺服器本來就會回的錯誤。

已抽成 `shippableMoves` 並用測試把三種情況都釘住。

### 付款後開通的一個關鍵細節

`provision_paid_order` 的呼叫**故意放在「狀態真的改變了」的判斷之外**。

如果放在裡面：第一次付款通知進來，狀態改成已付款，但開通課程時失敗了。
第二次通知進來，發現訂單已經是已付款，於是跳過整段 —— 這個會員就永遠拿不到課程。

放在外面，每次通知都會嘗試補開通，已經開通過的會被 SQL 條件擋掉。

### 純數位訂單會自己完成

沒有包裹要寄，就沒有人會去把它從「已付款」推到「已完成」。所以開通全部成功後自動轉完成。

但**只有在全部成功之後**。開通失敗卻標成已完成，等於用一個綠勾把問題蓋住。
