# 從 Strapi 吸收的 UI/UX — 待辦與取捨

2026-07-28

店主在本機跑了 Strapi 的官方 demo（LaunchPad），要求把它的 UI/UX 搬過來。**抄的是版面與操作方式，不是程式碼**：那份 repo 是 Next 16 + React 19 + Tailwind + Aceternity UI，我們是 Preact + 手寫 CSS，而且它根目錄沒有 LICENSE。所有東西自己寫。

以下是逐項看過之後的結論。每一項都寫了「為什麼」，因為半年後回來看，決定不做的理由比決定做的更容易忘。

## 後台

依實作順序。

### 1. 區塊組裝介面

Strapi 的 Dynamic Zone 是我們「頁面 + 區塊」的同一個東西，但操作差很多：

- 區塊是**收合的列**，收合時顯示「型別圖示 ＋ 型別 - 內容摘要」。我們現在全部永遠展開，一頁八個區塊要捲很久，而標頭只寫型別，看不出哪個是哪個
- 每列右側：刪除、**拖曳握把**、`⋯` →「在上方插入 / 在下方插入」。我們只能加在最後再用 ↑↓ 一格一格搬
- 加區塊是**圖示磚格**就地展開，不是 `<select>`
- **一個 Save 存整筆**，不是每個區塊各自一顆「儲存這個區塊」

最後一項是這裡最重要的。目前每個區塊自己存，意思是一次編輯會產生 N 次寫入，而且「我改完了嗎」沒有單一答案。

### 2. 首頁儀表板

後台的 `/` 現在是 ibon 列印——那是一個工具，不是首頁。改成儀表板：今天幾張待出貨、庫存告急的規格、本月營收、最近編輯過的頁面。ibon 移到工具區底下。

### 3. DRAFT / PUBLISHED 分頁

我們的狀態是表單裡一顆 radio。Strapi 把「我正在改的版本」和「顧客現在看到的版本」做成兩個分頁，隨時切著比對。防的是改到一半誤按公開。

### 4. 圖片自動產生 small / medium / large

前台目前把 1024px 原圖直接送給手機。這是會實際消耗顧客流量的事，不是視覺偏好。

### 5. EXIF 自動轉向

手機拍的照片上傳後會躺著。這是一整類 bug。

### 6. 列表頁三件套：搜尋、可疊加篩選、欄位顯示設定

篩選是 `[欄位▾][運算子▾][值]` 可以疊加。訂單頁最需要——現在只有一個搜尋框，「這個月還沒出貨的」查不出來。

### 7. 每列 `⋯` 選單 ＋ 勾選批次操作

訂單、商品、媒體都用得到。現在刪十張圖要點十次，而且每次都被瀏覽器原生的確認視窗打斷。

### 8. 並排預覽 ＋ 桌機/手機切換

預覽卡片已經有了，缺的是裝置寬度切換。顧客大多用手機看。

### 9. 媒體庫整包

拖放上傳（可多檔）、詳情改成 Modal 並顯示尺寸/格式/上傳時間、勾選批次刪除、格狀與清單切換、棋盤格底 + `contain` 不裁切、卡片顯示 `PNG · 1024×1024`。

**不做資料夾，改做 title + 標籤 + 搜尋。** 一張圖可以同時是「插畫」和「首頁用」，資料夾只能二選一；而且沒有資料夾就沒有「搬移」與「刪資料夾連帶內容」這兩個問題。

`title` 與 `alt` 是**兩個不同的欄位**，不能合併。alt 是給看不到圖的人讀的，內容取決於圖用在哪裡；title 是給店主找圖用的。合併的結果是為了好找而把 alt 寫成「首頁 banner v3」，然後讀螢幕的顧客就聽到這句。

標籤存**關聯表**而不是逗號字串：字串沒辦法建索引、列不出「現有哪些標籤」，而且搜尋會跨界誤中（搜「貓」命中「熊貓」）。

搜尋要**同時做進 MediaPicker**。只做在媒體庫頁面等於沒做——真正找不到圖的場合是插圖到頁面的時候。

## 前台

### 10. Footer 品牌欄

多欄連結我們已經有了（`footerColumns`，後台可編）。缺的是左邊那一塊：logo ＋ 一段介紹 ＋ 版權。現在連結欄從左排到右，沒有重心。加一個 `footerBlurb` 設定，版面改成「品牌欄較寬、連結欄靠右」。

這是清單裡最小的一項。

### 11. 商城的精選版面（1 大 + 2 小）

不是新的區塊型別，是現有 `shop` 區塊多一個版面選項。齊頭的 190px 方格把每張作品壓成一樣大，好作品沒有位置可以站出來——賣插畫的店，作品本身就是商品。

哪一張放大＝該區塊清單的第一個，不另外做「精選旗標」，否則要維護兩份順序。

**商品名與價格疊在圖上的浮動藥丸做成選項，預設關。** Strapi 那張是純黑太空底圖，字放上去乾淨；滿版構圖的插畫蓋上去很可能正好壓到重點。開啟時字放固定角落並加背景模糊，保證任何底圖都讀得到。

### 12. 聯絡我們（只做版面）

左邊聯絡方式、右邊一塊有氛圍的區域，做成一個 `contact` 區塊。

**表單送出不在這一項裡**，因為成本差一個數量級：CSP 目前是 `form-action 'none'`，後端也沒有接收端點。要做的話是新端點 ＋ 機器人防護（否則信箱會被灌爆）＋ rate limit ＋ 寄信 ＋ 放寬 CSP。而且我們已經有名片頁帶社群連結，顧客也能從訂單頁找到店主——表單多解決的只有「不想公開 email」這件事。

## 未確認

**SEO 欄位 ＋ Worker 注入。** 自訂頁面目前只有 `title`，分享到 LINE/IG 只看得到標題。要做的是每頁兩個欄位（分享描述、分享圖）加 Worker 注入。

關鍵前提：前台是客戶端渲染的 SPA，**在瀏覽器裡塞 `<meta>` 標籤爬蟲讀不到**——它們不執行 JS。所以必須由 Worker 在送出 HTML 前注入，而這個機制 [storefront.ts](../../../frontend/worker/storefront.ts) 已經為 `/card` 做好了，工作是推廣到其他路徑。

不做 `structuredData` 的 JSON 編輯器、也不把 `metaRobots` / `canonicalURL` 開成輸入框：填錯會讓整站從搜尋結果消失，而且看不出來。也不做 Good/Improvements/Bad 評分——規則要維護，而且會讓人去追分數而不是寫給人看的句子。字數提示涵蓋八成。

## 明確不做

- **Content-Type Builder**（讓店主自訂欄位）。我們的結構固定在 D1 的 migration 裡。開放自訂等於要動態 schema、動態遷移，再加一層能渲染任意欄位的前台。那是在做 CMS，而使用者只有一個人。
- **i18n 多語系**。只有中文一個顧客群。開下去每個欄位乘二、每個查詢多一個 locale 條件，而沒有第二種語言要填。
- **Roles / Users / SSO / API tokens**。使用者就一個。權限系統在單人系統裡是純負擔——多一套會出錯的東西，換不到任何隔離。
- **Review Workflows、Audit Logs**。那是「誰改的、誰審的、誰放行」，一個人的店沒有對象。訂單該有的稽核已經有 `order_audit_log`。
- **Releases、Content History**。概念不錯但複雜度高，而第 3 項的 draft/published 分頁已經擋掉大部分手殘。
- **圖片裁切編輯器**。範圍大，而店主的圖是自己畫的。
- **Marketplace / Plugins**。
