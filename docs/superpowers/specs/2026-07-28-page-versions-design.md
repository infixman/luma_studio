# 草稿、發行版、發行版歷史

2026-07-28

## 起因

一頁只有一份內容。`pages` 上的 `status` 決定它公不公開，`page_blocks` 就是它的區塊——沒有第二份。所以：

- 改到一半的頁面，只要它是 published，顧客就已經看到了
- 「我改完了嗎」看不出來，因為沒有「已發布的那一份」可以比對
- 發布之後想退回上一版，沒有上一版

Payload 用「自動存草稿 + 版本表」解決，每 100 毫秒存一次、`maxPerDoc: 50`。店主看過之後的決定是：**不要自動存**（一次編輯產生幾百個版本，要找回昨天的樣子反而更難），但要草稿、發行版、以及可以還原的發行版歷史。

## 決定

### 一份草稿，一疊發行快照

```sql
CREATE TABLE page_versions (
  id TEXT PRIMARY KEY NOT NULL,
  page_id TEXT NOT NULL,
  payload TEXT NOT NULL,
  published_at INTEGER NOT NULL,
  published_by TEXT NOT NULL,
  is_current INTEGER NOT NULL DEFAULT 0
);
```

| | 存在哪 |
|---|---|
| 草稿（編輯中） | `pages` + `page_blocks`，就是現在這兩張表 |
| 顧客看到的 | `page_versions` 裡 `is_current = 1` 那一列的 `payload` |
| 歷史 | 同一張表的其他列 |

現有的兩張表不改形狀，只是意義從「這一頁」變成「這一頁的草稿」。發布是把草稿序列化成一列快照。

### 快照存 config，不存接好的資料

區塊裡的商品價格、庫存與圖片是**讀取時**才接上去的（`block_data.hydrate`）。快照如果把接好的結果一起存，還原三月的版本就會把三月的價格一起搬回線上——那不是還原版面，是竄改價目表。

所以 payload 存的是區塊的 `type` 與 `config`，跟草稿一樣，讀取時照常 hydrate。**版本記錄的是版面與文字，不是商品狀態。**

### 還原是還原到草稿，不是直接上線

按下還原之後，舊版本的 payload 覆蓋草稿，頁面進入「已發布，但有未發布的修改」。要不要上線是下一個決定，由已經存在的「發布」按鈕做。

理由有兩個：你會想先看一眼；而且第二條上線路徑就是第二個會出錯的地方。

### 狀態變成三種

| 狀態 | 意思 |
|---|---|
| 草稿 | 從來沒有發布過，`page_versions` 裡沒有它的列 |
| 已發布 | 草稿與 `is_current` 的 payload 一致 |
| 已發布，有未發布的修改 | 兩者不一致 |

第三種是現在完全看不出來的：改完沒發布，畫面上沒有任何地方講。這也是編輯器 DRAFT / PUBLISHED 兩個分頁真正有東西可切的前提——在此之前那兩個分頁會顯示一模一樣的內容。

### 歷史封頂

每次發布寫一個 JSON blob，不設上限就是無限成長。**留最近 20 版，發布時刪掉更舊的。** 而且要在 README 寫明「不是無限」——不寫的話，總有一天有人以為三年前的版本還在。

## 附帶好處

前台讀一頁從「查 `pages`、查 `page_blocks`、排序、驗證每個區塊」變成「查一列、解析 payload」。比現在少一次查詢，而且 payload 在寫入時就驗證過了。

## 順序

1. `migrations.py` — `page_versions` 表與索引
2. `pages.py` — 序列化草稿、發布、還原、比對草稿與現行版本
3. `pages_admin_api.py` — 發布、版本清單、還原三個端點
4. `main.py` — `page_response` 與 `preview_response` 改讀 `is_current`；預覽讀草稿（那正是預覽的意義）
5. `PageEditPage.tsx` — 三種狀態的顯示、發布按鈕、版本清單、還原
6. `PagesPage.tsx` — 列表上的狀態改成三種

## 不做

- **自動存**。店主明確不要。一次編輯產生幾百個版本，反而讓「昨天的樣子」更難找。
- **草稿的版本歷史**。歷史是發行版的歷史——「這一頁曾經對外長什麼樣」是有人會問的問題，「我編輯到一半的第 37 個中間狀態」不是。
- **排程發布**。等有人真的需要在半夜上架再說。
